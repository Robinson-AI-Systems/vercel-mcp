## Findings

### VMCP-001 — P0 · D1/D2 · The purchase grant is still a product-scope wall for end users
- **Location:** `src/core/write.js` (purchase block), `src/core/write-preflight.js`,
  `src/vercel/spend.js` (`spendPreflight`).
- **Evidence:** any write whose declared spend is > $0, recurring, or unquantified
  cannot be completed by the caller's `confirm`: the executor demands a one-use
  purchase intent approved through separately authenticated owner setup
  (fingerprint-bound, ceiling-checked, expiring), and recurring/unbounded
  metered spend is refused outright outside one narrow Sandbox exception.
  Comment in code: "Agents may only PROPOSE a purchase."
- **Q1–Q3:** (1) limits the *user's* agent on an end-user connection, not only
  builders; (2) a wall — no standing delegation the user can set; (3) the escape
  hatch (per-transaction setup approval) works, but it *is* the ceremony the
  filed IN-08 answer (2026-10-17) declares not full end-user compliance.
- **Disposition:** *Convert* — per the filed answer and remediation issues
  #108–#110, #116, #119: end-user-chosen standing delegation policy per account;
  the one-use grant remains as the user's strictest option and stays mandatory
  for builder/delegated connections. Default strictness → owner packet OP-2.
  **OP-2 RULED 2026-10-27:** optional user-set budget + the owner's word is
  enough, even over their own budget (see the owner packet for the full
  ruled shape). The remediation now has its target design.
- **S7 (2026-10-28) — CLOSED.** The grant wall is refuted live on the
  owner's own connections. On both a project-scoped fixture connection and
  the owner's main team connection (standing policy read back by
  `vercel_whoami`: grant not required, no budget set), every spend preview
  evaluated the standing policy and framed its dollar line in owner-word
  terms; **no purchase intent was demanded at any point**, and metered
  execution was attempted on the owner's confirmed word alone (deployment
  and seed flows — both proceeded past authority into the provider
  segment). The production switch (VMCP-002) executed on the word through
  the same authority machinery. What still blocks metered *deployment*
  execution is a provider-segment defect, filed separately as VMCP-023 —
  it is not an authority wall: preflight's delegation was minted and the
  write dispatched. Recorded honestly: the built server contains **no
  fixed-price purchase tool** (the domain family has no buy tool), so no
  fixed-price purchase could be executed as a probe; the OP-2 probe ran
  as the metered executions above plus a build-resources change that was
  refused *legibly* as production-classified — correct behavior under the
  filed B2 definition, not a grant demand.

### VMCP-003 — P1 · D2 · IN-04: no token-expiry surface, no notify-ahead
- **Location:** `src/vercel/tokens.js`, `src/vercel/setup.js`, card O-3 (unbuilt).
- **Evidence:** the enrolled token's `token_expires_at` is stored and an expired
  token throws at use; nothing anywhere surfaces days-to-expiry or notifies

- **Disposition:** *Build* (O-3 scope) — expiry state in `vercel_whoami` and on
  the setup surface, plus the notify-ahead the ruling requires. The ruling's
  other half (no imposed term) already conforms: creation stores `expiresAt:
  null` unless the token itself carries one.
- **S7 (2026-10-28) — posture leg PROVEN LIVE; finding stays OPEN narrowed
  to the notify-ahead leg.** `vercel_whoami` on both S7 connections
  returned the AUD-E four-state posture exactly as designed:
  `expiryPosture: "unknown"`, "expiry not recorded for this token",

  expose a token's expiry to the server) instead of inventing a date. The
  notify-ahead leg could not be exercised: no enrolled token has a
  recorded expiry to warn on. Remainder: when a token's expiry is recorded
  (owner attestation / setup entry), the warning must fire ahead of it —
  that path is the open leg, owned by the O-3 revisit.

### VMCP-011 — P1 · D3/D10 · Oversized WRITE results throw after the provider write
- **Location:** `src/vercel/result-delivery.js` (`if (!readOnly) return
  shapeMcpResult(...)`), `src/vercel/shape.js` (default 8 KB `compact`).
- **Evidence:** executed probe 3 — the write path has no stored fallback, so a
  write whose result exceeds 8 KB returns a hard error to the caller even
  though the provider write was dispatched and journaled. The journal saves
  the truth, but the response contract breaks failure honesty: the caller
  cannot tell from the response that the write landed.
- **Disposition:** *Fix* — give write results the same stored treatment, or
  return the verified receipt (the `publicReceipt` machinery is the seed)
  with a handle to the full body.
- **S7 (2026-10-28) — stays OPEN, narrowed.** Live evidence: a 21-variable
  `vercel_env_list` result returned through the stored path exactly as
  designed (`status: "stored"`, a `res_` handle, preview, and the
  `vercel_get_result` next step) — the read side of the symmetry is real.
  On the write side, a `vercel_env_set_many` call with ten max-length
  keys landed at the provider (verified by read-back) but its response
  was a generic provider-error envelope, **not** the stored-handle
  verified receipt AUD-D designed — no `RangeError`, no crash, and the
  truth was recoverable by read-back, but the write-side receipt was not
  observed. Remainder: produce one live oversized write whose result
  returns the stored receipt, or file why the batch path cannot reach it.

### VMCP-027 — P1 · D8/D10 · The rtc deletion half is broken: cleanup deadlocks on unresolved intents, and the project-deletion inventory proof cannot pass against real records

Filed 2026-10-28 from the VMCP-023 closure probe's stranded run (fix
packet **AUD-K**; VMCP-023's closure cleanup leg depends on it).
**Live evidence:** the probe's scratch run could not be cleaned. Two
full `vercel_dev_cleanup` plan → confirm cycles returned `applied`
with `confirmed: false` and deleted nothing; the fallback
`vercel_project_delete` refused at the guard ("Could not safely
preview or classify the change") — on a project independently read
back as completely empty (every settings field null, zero
deployments). The same signature appeared at S7, where cleanup's
project delete landed *uncertain* and the orphan was removed from
the dashboard by hand.

- **D-A (proven, source): the intent deadlock.**
  `vercel_dev_cleanup` blocks a run's project object while any
  creation-intent object in the run is not `cleaned`, but
  `deleteExactObject` had no intent branch — an intent fell through
  to "requires its own guarded lifecycle" and could never be cleaned
  through the tool. An intent's outcome is set only on the seed's
  success path, so any seed failing after recording a creation
  intent strands its run deterministically, on every pass. The
  missing piece is reconciliation: proven absence of the intent's
  target clears it; an existing unrecorded target blocks honestly;
  an unprovable absence stays blocked.
- **D-B (proven, vendored schema): the unsatisfiable delete proof.**
  `inspectProjectForDeletion` (shared by `vercel_project_delete`
  and cleanup's project branch) demanded the project record carry
  `storageConnections` or `stores` as an array, `crons.definitions`
  as an array, `hasDeployments` as a boolean and a present `link`.
  The documented project schema (98 properties) contains neither
  storage field at all and does not require the other three, so the
  inspect throws for real projects generally — the direct cause of
  the live refusal and of S7's *uncertain*. The unit fakes model
  records **with** the invented fields (fixture blindness, fourth
  instance). No storage or cron list operation exists in the
  server's operation table either.
- **D-C (found by AUD-K's own tests): the intent-only run.** A seed
  failing at `projects_create` leaves exactly one intent object;
  cleanup's `targets()` filtered intents out, leaving an empty list
  the protected-resources guard denies as unidentified — the run
  could not even reach reconciliation.

**AUD-K delta (2026-10-28, this filing):** intents reconcile inside
cleanup on proven absence (the deployment inventory check reuses
the deletion proof's completeness discipline, `countComplete`);
intent processing is ordered before the project-block check, which
now reads reconciled state; each intent identifies its write target
(the project it concerned) so intent-only runs pass the guard;
the deletion proof is rebuilt on documented fields — storage demand
removed (recorded limit: no documented field and no list operation
exist for storage; store wiring surfaces as project env vars, which
the env inventory proves — adopt a documented storage surface when
one appears, by dated amendment), `link`/`crons` read as
documented-optional, `hasDeployments` kept as a conservative signal
with the scoped deployment list as the authoritative proof. Fakes
remodeled on the observed real record. **Closure:** the stranded
probe run discharged end-to-end through the fixed cleanup after
release, its project verified gone through the MCP and
independently. Noted, not claimed: one `vercel_project_list`
`unknown_error` in the same window ("provider did not return a
recognized safe error code") — undiscriminated; reproduce-or-drop
under this finding.
