## Two distinct ways to connect — Hub is optional

1. **Native remote MCP (primary for capable coding agents):** connect a client that genuinely supports **remote Streamable HTTP MCP and the required OAuth** to the service origin plus **`/api/mcp`**. The active origin must be the URL of this standalone service, not the Hub or a deployment preview of an unrelated application. `/.well-known/oauth-protected-resource` advertises the protected MCP resource and `/.well-known/oauth-authorization-server` advertises the service issuer/registration/authorization/token URLs. Server metadata has a stable technical identity `robinson-vercel-mcp`; owner-controlled display identity should be **Vercel by Robinson AI Systems**. Authorization is service-owned.
2. **RTC 1 HTTPS tool API:** the same standalone origin exposes the unauthenticated manifest `GET /api/contract` and schema `GET /api/openapi.json`. After separately authenticated owner issuance, supply a short-lived **`rtc_pass_...`** bearer ONLY in an HTTPS Authorization header. Start with `GET /api/whoami`, `GET /api/tools`, `GET /api/tools/<name>` and `POST /api/tools/<name>`; `GET /api/results/<handle>` is owner-bound. Pass grants are read-only preview or TEST service identity by default; since R-1W (2026-10-30) the owner may also issue a **write-capable** pass (`allowWrites`), which dispatches through the same guarded registry path as the MCP door — writes stay confirm-gated and spend stays under the pass's ceiling and the OP-2 delegation rules. A Hub client is never required for these direct doors.

**Never** put the passphrase, provider token, bearer, database URL or one-time secret in a chat, URL query, example issue, committed code, browser screenshot or assistant result. Use the sign-in flow's enrollment branch or the client’s secure OAuth/credential flow. Keep existing connection IDs/tokens stable when changing branding.

## Existing native MCP OAuth contract (source description, not external acceptance)

- The server advertises dynamic client registration `/api/oauth/register`, authorization `/api/oauth/authorize`, token/refresh `/api/oauth/token`, and exact resource binding to `/api/mcp`. Current implementation requires authorization code with S256 PKCE, and **client_secret_post or secretless public-client `none`** for dynamically registered clients. Token responses include 3600-second access tokens and a refresh token; refreshing rotates it and a reused/expired/revoked credential is refused.
- During sign-in select the correct previously enrolled owner Vercel account/team and enter the administrator passphrase — that is all the consent form asks. Profile, mode and listing are **derived at issuance, never selected** (AUD-AZ): profile is full for every sign-in (AUD-BD — the door decides the credential's reach, not the profile), mode from the account's own production switch — which is on from enrollment, so a normal sign-in starts in production — listing always the front door. Profile, account and production authorization are enforced server-side; merely asking an agent to change profile does not grant permissions.
- The provider Vercel API credential is enrolled by the owner through the sign-in flow's enrollment branch (`/api/oauth/enroll`), which probes it and reads back its granted scope before anything is stored, and it is never passed to the coding agent. A service OAuth token and a Vercel provider API token are different credentials and must not be confused.
- The updated source supports `token_endpoint_auth_method=none` public clients **without** generating a secret, and existing `client_secret_post` confidential clients, both with S256 PKCE and exact resource/redirect validation. Public-client source tests and real disposable-Postgres refresh-race proof were added in PR #219; the owner's desktop connector interoperability is verified in daily use (2026-10-30, `docs/STATUS.md`), while the formal per-client matrix and mobile interoperability remain unverified. Client ID alone is not sufficient to use a code or another client's refresh credential. Do not embed a shared secret in a mobile application.

## Desktop and mobile setup without unverified compatibility claims

For a capable desktop coding agent, open its remote/custom MCP connector settings, enter the standalone server's verified HTTPS origin plus `/api/mcp`, choose its normal OAuth connection flow, select the enrolled Vercel account during server authorization (profile and mode are derived, not selected), and complete its browser callback. Run a genuine `vercel_whoami` then an authorized provider-scoped read such as `vercel_list_accounts`; compare the selected team ID to the Vercel account you intended. The actual documented user-interface menu labels vary by client and platform.

For mobile, use the same remote HTTPS endpoint **only if the specific mobile client supports remote custom MCP and the described secure OAuth flow and browser redirect**. A mobile browser that opens the sign-in page or a ChatGPT plugin that shows installed does not establish remote MCP support on that coding agent. There is no independently verified mobile client acceptance in this repository as of this date. Where the platform does not support the flow, use its documented supported integration or an authorized desktop environment; do not require a desktop IDE to operate the hosted service itself.

For the independently scoped RTC API, first issue the pass on the owner's own connection (`vercel_issue_pass`), or propose it with `vercel_create_pass` and have the owner apply it with `vercel_apply_owner_approval` — **read-only** for reads, or write-capable (`allowWrites`, R-1W) only when the task genuinely needs writes — set approved areas and expiry and the rate limit (1–600/min; 120 default for new passes); the bearer is delivered once as a one-time secret through `vercel_reveal_one_time_secret`. Securely give it to the capable HTTPS client and perform a real permitted read. `TEST` passes intentionally cannot call Vercel. A successful TEST `vercel_whoami` verifies this service only.

## Diagnose and recover without widening access

| Symptom | Owner-safe verification and recovery |
|---|---|
| Missing remote MCP/connection menu | Confirm that exact client and version support remote MCP on that platform; mere mobile app access is insufficient. No unsupported compatibility claim. |
| OAuth issuer/resource/callback rejected | Check that deployment origin matches configured `PUBLIC_BASE_URL` and registration redirect. Check that the client supports the advertised PKCE and token authentication. Never paste secret into chat. |
| Connected but no tools | Check chosen team, the derived mode/profile/listing `vercel_whoami` reports, the account's read-only switch, real deployed `live` revision and correct connector identity. Discovery alone is not provider execution. |
| Missing access to a Vercel project | Check the actual stored provider token scope and the user’s delegated role; an account “whoami” read is not proof of project ownership, production access or spending permission. |
| Expired/refresh failure | Let the client perform a normal refresh once. A failed rotation/reuse must not be retried with stale tokens; disconnect, independently reauthenticate and consent to reconnect. |
| Revocation needed | Revoke a selected owner connection on the owner's own connection (`vercel_revoke_connection`, owner-applied) or an RTC pass with `vercel_revoke_pass`; confirm that the old token now fails, then reconnect and verify the intended account. Do not clear unrelated credentials. |
| RTC 429 | Check the pass-specific limit and the documented `Retry-After` response. Do not evade Vercel provider's independent rate limits. |
| Write or spend refused | Determine whether a true user credential/scope, intentional user approval, protected-resource rule, or a developer-policy rule that has not been delegated to the end user caused it; if it is the last, file it against the authority audit (`docs/PRODUCT-AUTHORITY-AUDIT.md`) — do not bypass a guard or claim full authority when only reads work. |

## Required evidence before calling a client supported

For **each** independently supported desktop and mobile client, record: exact client/version/environment; service hostname and serving source SHA; fresh client registration/authorization without exposing credentials; MCP `initialize`, authenticated `tools/list` and real provider-scoped `tools/call`; safe approved disposable write plus independent provider readback if delegated; expiry/refresh, owner revocation, reconnect; unauthorized tenant/resource refusal and failure without a mutation. Separate the unit/fake DB results from actual client/provider evidence in `docs/STATUS.md`, existing acceptance queue and R cards.
