# W-5 — Env sync + rotate secret (Batch W, fifth card)

Design: `docs/designs/BATCH-W.md` §3 rows W6, §4 row W-5.
Dossier: `batch-w-dossier-2026-10-30.md` §1 (W-5 rows).
Precedent: Batch P verdicts C-1..C-9; W-2..W-4 write composition.

## Scope

Two guarded writes in `src/tools/workflow-env.js`:

- **`vercel_workflow_env_sync`** (Cp, everyday+full) — description
  `{project, destinationProject?, sourceTarget, destinationTarget,
  keys?, outsideApp?}`. Plans from `vercel_env_list` on both sides
  (values are never read by the workflow): one `vercel_env_copy` step
  per source name the destination lacks on the destination target
  (branch-matched on preview), each step carrying the source row's
  exact identity (`sourceId`, `sourceUpdatedAt`) the copy tool's own
  contract demands. Names already consistent are skipped.
- **`vercel_workflow_rotate_secret`** (PR, full) — description
  `{project, key, targets?, outsideApp?}`. Step 1 dispatches
  `vercel_env_set` in update mode with
  `generate: {bytes: 32, encoding: 'hex'}` — the fresh value is minted
  inside the step's own pipeline and never appears in any workflow
  argument, result or journal. Step 2, only when the variable targets
  production and a live deployment exists, dispatches
  `vercel_deploy_redeploy` of the current live deployment with its
  read-back `expectedState`/`expectedTarget`.

## Verdicts recorded on this card

- **W5-C1 (capped inventories):** `vercel_env_list` caps at 100 rows
  and self-reports `completeness: 'unverified_provider_page'`. A plan
  built on a capped list could silently skip names, so sync refuses
  when either side is capped — unless `keys` names the subset and
  every named key is present in the returned source rows. A named key
  absent at the source refuses by name (a likely typo is a question,
  not a skip).
- **W5-C2 (what cannot move is reported, never stepped):** the copy
  tool's contract moves only Config-kind rows whose targets exclude
  production, from a preview/development source target. Secret-kind
  source rows are listed in the preview and the report (the design's
  rule); Config rows the copy contract cannot move (production in
  their target set) are reported as not-syncable with the reason.
  Neither becomes a step the workflow knows will refuse.
- **W5-C3 (rotate refusals are the workflow's own):** rotate refuses
  before planning when the variable is Config-kind (rotation mints a
  random value; changing a Config value is a deliberate
  `vercel_env_set`), when the name is `VERCEL_*` (Vercel manages
  those itself), and when a covering stored profile lists the key in
  `managed_env` (the design's W6 rule; the app guard inside the
  step's pipeline enforces it again). When several rows carry the
  key and no `targets` disambiguate, it refuses naming the target
  sets on file.
- **W5-C4 (who else must learn the new value):** no profile field
  names secret consumers today, so the receipt carries the honest
  general lines: new deployments use the new value automatically
  (and the redeploy covers the live one); any system outside Vercel
  sharing the secret must be re-issued on its own side, because the
  generated value is never shown — by design, not by omission.
