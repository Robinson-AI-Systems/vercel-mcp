# R-1W — Write-capable RTC passes (R-1 remainder)

Status: implemented in this PR. Batch R card completing R-1's write-pass remainder (design: docs/designs/BATCH-R.md R-1 + the 2026-10-30 amendment adopting the `rtc_passes` model for writes; tail dossier §2, 2026-10-30). Also closes UA-06's remaining leg (docs/PRODUCT-AUTHORITY-AUDIT.md).

## Scope

- **Design amendment first** (same PR, before the code it authorizes): BATCH-R.md gains the dated 2026-10-30 amendment the 2026-10-27 resolution requires — `rtc_passes` adopted for writes, with allow-writes, spend (OP-2 / BATCH-B D-A delegation shape) and revocation semantics defined there. Owner ratifications recorded: pass storage = `rtc_passes` (2026-10-30); B-8 §5 ratified.
- **Storage (additive)**: `rtc_passes` gains `allow_writes BOOLEAN NOT NULL DEFAULT FALSE`, `spend_limit_cents INTEGER NOT NULL DEFAULT 0`, `project_ids JSONB` (NULL = unrestricted). Existing rows behave byte-identically: a read pass is `allow_writes = false`, and the read-only inspect/authorize predicates are preserved verbatim for it.
- **db**: `issueWriteRtcPass` (profile everyday/full, mode preview/production, areas, spend ceiling, optional project list, rate limit, lifetime) beside `issueReadOnlyRtcPass`; `inspectRtcPass`/`authorizeRtcPass` extended so a write pass authorizes under its own predicates while read passes keep the existing SQL predicates exactly. Revocation is the existing `revokeRtcPass` (any pass row).
- **Issuance**: pass-request payload v2 carries the write scope (`src/vercel/pass-requests.js`); v1 payloads still decode and still issue read-only passes. `vercel_create_pass` gains optional write-scope arguments (still approvalOnly, full profile only; its description grows to name the write form). The setup review page states a write scope in plain words before approval; the direct setup issue form gains the write options. Every issuance path remains behind the administrator passphrase (R-1's production + writes rule).
- **Door** (`src/rtc/door.js`): `validPassRecord` accepts a write pass under the amendment's shape; listing/describe/invoke expose a write tool only when the tool's registered profiles include the pass profile, its area is in the pass areas, and it is a guarded write. Invocation runs the shared registry dispatcher — the tool's exact `defineWrite` lifecycle is the write path; no second executor. `_batch` stays read-only. `vercel_whoami` on a pass reports its write capability and spend ceiling.
- **Spend seam** (`src/core/write-preflight.js`): on a pass connection, the purchase branch enforces the pass delegation — spend-classified writes refuse when the ceiling is 0; a fixed known price at or under the ceiling proceeds journaled as a pass delegation (never `owner_word`); recurring or unquantified spend always refuses. Keyed on server-minted pass fields on the frozen connection; caller arguments cannot set them.
- **Project-scope seam** (write executor): when the pass carries `project_ids`, a write refuses unless every declared target resolves to a listed project (`target.projectId`, or `target.id` for `kind === 'project'`, or `target.project`); a write with no resolvable project target refuses (scope unprovable). Checked after targets are computed, before dispatch.

## Drift check A

| Assumption | Evidence | Resolution |
|---|---|---|
| Write passes need a new executor | `dispatchReadOnlyTool` in `src/core/mcp-server.js` is the registry's general dispatcher; `defineWrite` executors are reached through it on every door | The door dispatches writes through the same seam; the pass-specific gates live in preflight + the executor's project-scope check, not a parallel pipeline |
| The grant path can serve pass spend unchanged | `write.js` `purchaseDelegationFor` accepts only `basis: 'owner_word'` for apply-side re-checks; a pass is a delegated credential, never the owner's word | A distinct pass delegation basis minted only from the frozen connection's server-set pass fields; recurring/unquantified still refuses, as on the grant path |
| `vercel_create_pass`'s description can grow freely | Pass-proposal checks pin description content | The card names the growth; pins are updated to the new exact text in this PR, never loosened |
| Read passes might authorize differently after the predicate change | `authorizeRtcPass`'s SQL hard-requires `profile='read_only'` today | The extended predicate is a disjunction: the existing read predicate verbatim OR (allow_writes AND write-pass shape); db tests pin read-pass behavior before/after |

## Verification

Fake-provider tests only; no live pass is issued. Verified locally on this VM (unit via vitest directly; database tests against a disposable local Postgres 16 cluster), then by exact-head CI.

- **Unit — door + dispatcher seams** (`tests/unit/rtc-write-passes.test.js`, 11 tests): a write pass lists/describes/invokes a real guarded-write fixture while a read pass gets `outside_scope` and never applies it; a write-shaped row that is not a guarded write stays invisible; preview → needs_confirmation → applied through the shared executor; a $3.00 fixed price under a $5.00 ceiling applies with the journaled delegation `{basis:'pass', ceilingCents:500, quotedCents:300}` visible to apply; over-ceiling, recurring, unquantified and zero-ceiling spends never apply, with refusal reasons pinned at the dispatcher (`exceeds the spend ceiling on this pass`, `Recurring or unquantified spend cannot be delegated to a pass`, `Pass spend authority cannot be verified` for an unminted pass connection); the project restriction refuses out-of-list targets (`restricted to specific projects`) and allows listed ones; the batch route refuses any write call while still serving reads; whoami reports `writes:true` + ceiling for a write pass and is byte-identical for a read pass.
- **Unit — proposals + setup** (`tests/unit/pass-proposals-write.test.js`, 4 tests; `tests/unit/setup-write-passes.test.js`, 3 tests): the write preview states profile/mode/ceiling/projects in plain words; malformed write scopes and write-only arguments on a read proposal refuse; the full propose → owner review (scope stated in plain words) → approve flow issues exactly the proposed scope via `issueWriteRtcPass` and the request cannot be consumed twice; the direct setup form parses the dollar ceiling to cents (`25.50` → 2550), parses the project list, and refuses forged CSRF, wrong passphrase, preview deployment, malformed ceilings/areas/modes/profiles. The proposal description pin was updated deliberately to the new exact text (names both forms); the old negative pins (`allow_writes`, `spendLimit` arguments) still refuse.
- **DB — throwaway Postgres** (`tests/db/rtc-write-passes.test.js`, 6 tests; `tests/db/pass-request-v2.test.js`, 3 tests; `tests/db/rtc-pass-migration.test.js`, 2 tests): issue/inspect/authorize round-trip preserves profile, ceiling and project list and journals `vercel_owner_issue_write_pass`; defaults are everyday/preview, ceiling 0, projects null; invalid issuance shapes throw and an unknown account issues nothing; read-pass inspect/authorize results carry no write fields (byte-compatible); corrupted mixed-shape rows (allow_writes stripped, TEST mode with writes, read_only profile with allow_writes) refuse at inspect and authorize; the per-minute window and revocation work for write passes; payload v2 round-trips encrypted through inspect + one atomic consumption and never decodes against read-only areas, while v1 stays v1; a legacy table gains the three columns with read-only defaults (allow_writes false, ceiling 0, projects null), idempotently.
- **Regression**: the pre-existing pass suites (`rtc-passes`, `pass-request-inspection`, `rtc-http`, `rtc-api`, `rtc-manifest`, `pass-proposals`, `rtc-owner-passes`, `owner-export`, write-contract/preflight suites) pass unchanged except the deliberate surface changes named on this card (proposal description text; the door's generic `refused_by_guard` wording; whoami's added write fields — read whoami is byte-identical).
- **Incident recorded**: the file-write path had redacted the token-prefix string literal inside `issueWriteRtcPass` to a placeholder before this stage began; the db tests caught it (issued tokens failed the wire-format check) and the literal was repaired and re-verified byte-for-byte. Fake-shaped fixtures only throughout; no live pass was issued and no live tool was called.
