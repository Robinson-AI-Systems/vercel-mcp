## D-2a (#132): two useful non-mutating deployment reads

- `vercel_deploy_list({project?,limit?:1..20,until?})`:
  `deployments_list` GET `/v7/deployments`, query `projectId`,
  `limit`, `until` and **server-stored** team ID. For team scopes an
  explicit project ID is required; project-key connections default to and
  cannot escape their stored project. Provider project IDs must agree on
  every row, and pagination must be complete and consistent. A page reports
  its real continuation, never a fabricated global total.
- `vercel_deploy_get({deployment,project?})`:
  `deployments_get` GET `/v13/deployments/{idOrUrl}`. Accept a clean
  deployment ID or HTTPS hostname; never fetch a user-supplied URL.
  Independently compare returned `projectId` to the authenticated scope.
  Return only ID/project, state, target, timestamps, safe hostname/alias,
  Git commit/branch and bounded error code; no raw metadata/logs/secrets.
- Acceptance: `tests/unit/deployments.test.js` exercises fake HTTP
  transport, request-shape/OpenAPI validator, team/project scope, cursor,
  hostile input, provider identity, ID/URL agreement and no mutation.
  GitHub Actions exact-head check/unit/db/emulate/ci/release-policy required;
  this is **not** live custom-MCP provider acceptance.

## D-2b (#134): bounded build-log diagnostics and source file tree

Added verified-project GETs `/v3/deployments/{idOrUrl}/events`
(non-following, 100 events max requested) and `/v6/deployments/{id}/files`.
Each tool first independently GETs the deployment and verifies its
returned ID and project against the encrypted server-held connection;
a caller cannot use another team's/project's ID. Log summary scans up
to 5000 events, counts errors/warnings/commands and returns first
error's event index and safe step (never raw log text). Completeness is
*unknown* without a trustworthy provider cursor. File tree returns
first 20 safe paths and bounded traversal; absent tree is unknown, not
proof of an empty deployment. No source bytes are returned.

Provider REST/OpenAPI shape, fake-HTTP cross-project refusals,
secret-bearing log/path omission, overdeep files and long fixture
regressions are in `tests/unit/deployment-diagnostics.test.js`.
This is implementation + offline CI only, NOT genuine connected acceptance.

## D-2c (#135): Checks V2 read diagnostics

Implements `vercel_check_list_project_checks`,
`vercel_check_list_runs` and `vercel_check_get_run`.
Official pinned provider GETs are /v2/projects/{projectIdOrName}/checks,
v2/deployments/{deploymentId}/check-runs and
v2/deployments/{deploymentId}/check-runs/{checkRunId}.
Each project is independently re-read from the stored account scope;
deployment check runs use the shared D-2b provider ID+project proof
first. Any conflicting project/deployment/run ID is denied. Project
check lists and deployment run lists expose at most 20 field-projected
safe names/status/conclusions/tasks and never raw integration outputs.
Provider page completeness stays unknown until verified.

`tests/unit/checks-read.test.js` covers pinned GET request mappings,
cross-project denial, output omission, malformed rows, duplicate IDs,
uncertain completeness and account binding. CI passing is not evidence
of real Vercel provider or custom RTC 1 deployed acceptance.

## D-2d (#136): deployment status waiting without long-running Basic invocations

Adds `vercel_deploy_wait({deployment,project?,waitSeconds?:0..8})` through the existing
pinned GET /v13/deployments/{idOrUrl}. Revalidates the stored account, provider
deployment ID and returned project on every poll, including after a transition.
At most three reads and a short request timeout bound each call; the function
never promises a 45-second blocking wait, and an incomplete build returns a
clear next-call instruction. READY/ERROR/CANCELED are terminal after readback;
unknown or unfinished state stays `done:false`. This remains a read-only D-2
early-start slice, not a deployment or hosted connection acceptance.

Automated evidence: `tests/unit/deploy-wait.test.js`, existing transport
validation and repository-wide Actions checks. Real serverless runtime
duration and Vercel token acceptance remain unverified.

## D-2e (#137): runtime log stream sampler with strictly bounded transport

The pinned official REST GET /v1/projects/{projectId}/deployments/{deploymentId}/runtime-logs
offers a stream (not a finite JSON list). Its documented query selectors are
teamId and slug only, so the MCP filters timestamps and severity locally.
`vercel_deploy_get_runtime_logs` independently proves account/project/deployment
identity before fetching a bounded **32-KiB / 50-row / 6s maximum** streamed
sample. The tool defaults to a 30-minute window (maximum 24 hours);
optional exact level, HTTP status and path filters are evaluated privately.
It returns counts and transport truncation, never raw request paths, messages,
domains or sensitive metadata. Even provider stream EOF is **not** claimed
to prove no more logs exist. Tests: `tests/unit/runtime-logs.test.js`.
No live provider, HTTPS custom MCP or Hub direct/relay/Sandbox acceptance.

## D-2f (#138): find the relevant deployment before inspecting it

The pinned Vercel GET /v7/deployments supports `state`, `target`, `branch`,
`sha`, `since` and the existing `until` cursor. Extend the authenticated
project-scoped `vercel_deploy_list` with finite allowlisted filters while
retaining 20-row limits and clear pagination. Provider rows must match
their project and requested state, target, branch and SHA; the continuation
keeps the same filter context. No write, permission or account expansion.
`tests/unit/deployment-filters.test.js` covers the pinned fake GET query
mapping, errors, identity, pagination and forbidden query parameters.
This is offline/CI only, not deployed provider or Hub acceptance.

## D-2g (#139): byte-bounded file content transport

The pinned GET /v8/deployments/{id}/files/{fileId} documents base64 JSON but
does not guarantee the successful payload property names in the public SDK.
Implement a **fail-closed** small text reader: independent deployment/project
GET and file-tree membership verification, no arbitrary file ID or team
override, 8 KiB HTTP JSON cap *before parsing*, strict canonical base64, ≤2
KiB decoded UTF-8, credential/sensitive-path screening and exact IDs when
present. Binary, oversized, sensitive and unrecognized responses fail closed,
with no truncated success. Tests: `tests/unit/deployment-file-content.test.js`.
Actual provider response shape and deployed owner custom MCP proof remain
UNVERIFIED; passing mocks cannot certify this endpoint works against a
real deployment. No production writes, resource creation or paid calls.

## D-2k (#171): truthful optional source-tree availability
Verified October 13 against the actual saved custom Vercel service and an
independent provider read: `GET /v6/deployments/{id}/files` returned HTTP 404
for the exact READY Git-sourced service deployment, despite a positive prior
`GET /v13/deployments/{idOrUrl}` identity result. Vercel only guarantees a
retrievable source tree for deployments built from CLI/API uploaded files.

`vercel_deploy_list_files` now classifies *only* this endpoint's 404 after
positive deployment/project scope proof as `availability:not_exposed`,
`complete:false`, and an explicitly **unknown** source inventory.
It must not suggest that the verified deployment is gone, nor that it contains
zero files. Permission, network and upstream 5xx errors still fail; the strict
file-content reader is unchanged. Fake provider regression runs in CI;
connected acceptance of this source revision requires checked deployment
before marking the new behavior observed. No production mutation or spending.

## D-2j (candidate #160): safe connected evidence runner

`scripts/check-connected-acceptance.mjs` makes actual direct HTTPS
acceptance repeatable with owner-injected *protected* short-lived RTC TEST
and preview passes; no pass is created or returned by the script. Before
any privileged check it validates the public contract, exact OAuth issuer,
anonymous denial, TEST service-only allowlist and provider denial.
On an owner-approved nonproduction deployment it verifies preview pass
scope, write denial, actual bounded runtime sample metadata and optional
file identity/UTF-8 length/SHA-256 against a previously known harmless file
digest without recording contents. After **external owner revocation** it
independently checks 401 for each previous pass. Every HTTP response is
bounded to 8 KiB, redirect refused, timeout 7 seconds, raw bodies and
credentials never printed. Unit tests use fake fetch only.
A nonzero real runtime sample and correct file digest are different
observations from mocked CI and do not imply upstream completeness.
Neither true original OAuth MCP login nor Toolkit Hub relay/Sandbox
acceptance is replaced by this runner. Re-entry needs two short-lived
owner-issued passes and an explicitly authorized disposable deployment;
the runner does not create it or change production.

## D-2l (#172): runtime streaming content negotiation and empty-success semantics

Real custom runtime-log attempt returned an unclassified provider error at the
previously verified READY deployment, despite a separate standard provider log
query returning no matching records in its queried 30-minute range. Source
review found a protocol mismatch: the custom transport requested ordinary JSON
for a documented streamed endpoint. The pinned runtime GET now sends
`Accept: application/stream+json`, leaving all other API reads as JSON; a
successful 204 response is a safe, empty, **incomplete** sample rather than a
null-body reader failure. Stream length/time/row caps, project/deployment
identity proof, secret scrubbing and malformed-stream refusal remain intact.
The regression suite verifies the actual outgoing Accept header, unchanged
ordinary GETs and no-content partial result. Real connected success remains
pending a checked release and separate owner-scoped acceptance; no synthetic
provider proof or production mutation is claimed.
