Client behavior: inject the team ID as teamId; enforce a 25-second timeout; validate every request against the snapshot; retry GET/HEAD/DELETE once on network error or 5xx; never auto-retry POST/PUT/PATCH; translate 429 into rate_limited and retry a read only once when reset is within five seconds. A request key is stable across retries and excludes dryRun, confirm, fields, and detail; a caller-provided requestKey overrides it. Repeated keys within ten minutes return the safely stored result without another provider call. Pagination stops at its configured cap and reports capped.

## Replay storage implementation correction (2026-10-11)

The approved A9 design requires a durable, cross-instance, ten-minute claim before a write, but `change_log.request_key` has only a nonunique index and cannot atomically reserve a key. A read-then-write check could double-charge or double-create on concurrent serverless instances. This card therefore uses its allowed **one additive migration**, `request_replay` with a unique primary key, instead of falsely claiming replay safety with a non-atomic audit lookup. The change is an implementation of the already-approved A9 behavior, not a policy relaxation. Claims are exclusive, pending outcomes require read-back, and a changed claim cannot complete an older reservation. Add a disposable-Postgres concurrency regression before merge.
