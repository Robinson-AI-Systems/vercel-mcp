# AUD-AA — Account-row removal surface (owner step 4 tooling gap)

**Naming:** the AUD letter sequence continues past AUD-Z; AUD-AA is the next free card ID. This implements work-order item 1 from the audit coordinator (2026-10-30): the tooling gap the VMCP-026 acceptance filed at owner step 4.

**Baseline inspected:** main `f802d00` (AUD-M2). Built dossier-first — the full contract dossier is `account-removal-dossier-2026-10-30.md` in the audit goal workspace (every surface read in code before any fix was written).

**The gap (re-verified, not inherited).** The product can enroll, re-probe, spend-limit, default-select and connector-revoke an account, but no surface anywhere removes an enrolled account row: no `DELETE FROM vercel_accounts` in `src/db.js`, no remove action among the setup page's form actions, no catalog tool. Owner step 4 (remove the rtc-scratch fixture account record) is authorized (Chris, 2026-10-29 22:40 MDT) but unexecutable, and the A-14 narrow probe token's dead credential record (token deleted at Vercel) is likewise unremovable. This card ships the capability only — the live removals are owner acts that ride the next release; no live removal is attempted here.

## Design (decisions, with reasons — full shape map in the dossier)

- **Beside revoke, never conflated with it.** `vercel_revoke_connection` kills one connector credential's standing and keeps the enrollment; removal deletes the enrolled row itself — the stored Vercel credential and everything scoped to the enrollment. One act must not silently do the other's job.
- **Both surfaces, one operation.** A new owner tool `vercel_remove_account` (the envelope's fourth action, `remove`) and a direct setup-page section mirroring the revoke section (select + confirm + fresh passphrase), because anything the owner can do by hand his agent can propose through the tool. Both execute through the single atomic db operation `db.removeOwnerAccount` → plpgsql `rmcp_owner_remove_account`; neither surface has a private mutation path. The tool joins `LOCAL_OWNER_TOOLS` in the same change (the AUD-Z reachability lesson) and the RTC owner-audience label set.
- **Cascade — credentials never outlive the enrollment.** Account ids are derived (team / team+project / user), so re-enrolling the same team recreates the same id; any credential left live would silently regain its standing (preview tokens immediately, production when the switch is re-enabled). Inside the one transaction, under the target row's lock (the revoke function's serialization precedent): live `oauth_tokens` and `rtc_passes` are **revoked** (not deleted — the conn_ id derivation and audit trail survive); unconsumed `oauth_codes`, `pending_inputs`, `one_time_secrets` and account-scoped `protected_resources` are **deleted**; `change_log` history and `purchase_intents` are **retained** (the journal is the record; an intent cannot execute without the account's credential). The audit row written in the same statement carries the cascade counts and `wasDefault` — never token material.
- **Guards from the shape map, refusals classified (IN-18).** Unknown target refuses at both layers. The **default guard**: the new-connection default is `listVercelAccounts()` ordering (`is_default DESC, label ASC`) and the consent page falls back to `accounts[0]`, so deleting the default row while others remain would silently promote the alphabetically-first survivor — refused with its remedy (choose a new default first), enforced at proposal time, in the envelope request, and again inside the plpgsql under lock, because approval-time state is the truth. The function returns a TEXT status (`removed` / `missing` / `is_default`) precisely so the two refusals stay distinguishable — the one deliberate deviation from the revoke function's BOOLEAN.
- **Disclosures, not gates.** Self-removal is allowed: the owner's approval happens on the setup page under a fresh passphrase, an authority independent of the connection being removed, and the plan says in plain words that this connection stops working. Last-account removal is allowed: zero enrolled accounts is the fresh-install state and the setup page (passphrase login, `add_token`) re-enrolls without any account row. Production-enabled is disclosed and allowed (IN-09: the switch is the owner's). Refusing any of these would recreate the authorized-but-unexecutable gap this card closes.
- **The plan names what points at the row.** The proposal's preview is built from one db read (`getAccountRemovalFacts`): label, scope, team slug, token last4, posture (default/production/self/last), and the exact cascade counts as read at proposal time; the atomic operation re-derives them at approval time and the audit row records the approval-time counts.

## Boundaries

No schema migration (the function is `CREATE OR REPLACE` in `initSchema` beside `rmcp_owner_revoke_connector`; tables unchanged). No front-door change: owner tools are not front-door, the compact door is unchanged, and the catalog grows 237 → 238 in the "Server about itself" family (20 → 21; hand-built 233 → 234) — catalog note in this card's first commit per checklist B. No behavior change to the existing three owner actions (their payloads, validation and summaries are byte-identical; the shared sets gain one member). Chris's real account row is never touched by this card: it ships the capability, exercised only against fake fixtures.

**Acceptance.** Unit: the proposal seam (listing/gating by profile incl. direct invocation, plan text with counts and disclosures, envelope issuance exactly once with a `remove` payload, default-guard and unknown-target refusals issuing nothing, injected-arg refusal) and the setup handler's posture (production + confirm + passphrase gates, classified 409s, panel renders the section). DB (throwaway Postgres): the atomic operation's cascade verified row by row, the default guard refusing while a second account exists and lifting once the default moves, sole-account removal, `missing` on repeat, exactly one audit row carrying counts and no fixture secret, envelope end-to-end (issue → consume → apply → row gone), and concurrent double-removal yielding exactly one `removed`. The boundary test's owner-set pin grows to eight tools, so a future localAdmin tool missing from the boundary list fails CI by construction. Live closure rides the next bundled release: owner step 4 executes against the fixture row and the dead A-14 record on the released build, verified by the setup page's account list before/after.
