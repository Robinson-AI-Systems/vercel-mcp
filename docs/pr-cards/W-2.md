## Scope

Two tools in `src/tools/workflow-deploy.js`:

- `vercel_workflow_why_did_build_fail` (read, all profiles). Resolves
  the deployment (project argument optional — projects are probed in
  order when it is omitted), then composes `vercel_deploy_get`,
  `vercel_deploy_get_build_logs` and `vercel_check_list_runs`. Renders
  the first error (build step + event position, from the area tool's
  screened summary — raw log text never leaves the area tool, so the
  unredacted line is pointed to in Vercel), a likely cause and exact
  fix keyed to the failing step, failed check runs as evidence, and a
  redeploy-would-help verdict: a same-commit redeploy is said to help
  only when the build log carries no error events (infra-class
  failure); a code-step error is reported as "will fail the same way".
  A deployment that is READY, still building or canceled is reported
  as what it is, never as a build failure.
- `vercel_workflow_deploy_and_wait` (guarded write, Cp, profiles
  everyday+full). One `description` object argument (C-9):
  `{project, branch, sha?, target?, outsideApp?}`. `before()` resolves
  the project to its exact id/name and the exact commit — the caller's
  full 40-character `sha`, or the newest deployment on the branch
  (its recorded commit); with neither available it refuses, naming the
  remedy. The single step dispatches `vercel_deploy_create_from_git`
  (derived request key `<key>-s1`, P-3 pattern): preview is the step's
  own dry-run where it can run. After the create applies, the workflow
  reads the deployment back from the branch list and polls it with
  `vercel_deploy_wait` dispatches under the module's 45-second budget;
  on READY it attaches the check-run summary. A budget stop returns
  the deployment id and the exact `vercel_deploy_wait` continuation —
  never a suggestion to re-run the workflow (that would create a
  second deployment). On an everyday connection the create step's own
  full-profile refusal surfaces as the stop reason, verbatim from its
  envelope (dossier §1 W-2 verdict; never routed around).

## Verdicts recorded on this card

- **W2-C1 (spend):** the catalog row's Safety mark is `Cp` with no `$`,
  so per amended C-4's own logic the workflow declares no `spend()` of
  its own (check-writes enforces the match both ways). The metered
  build spend is the create step's, and its purchase policy runs
  inside its own dispatched pipeline.
- **W2-C2 (poll placement):** polling lives in `apply()` — the
  deployment exists only once the create lands; `verify()` is a
  single read-back of the created deployment.
- **W2-C3 (cause rendering):** likely cause / exact fix are keyed to
  the failing build step and the error tally only. No log text is
  available to compose from (the area tool never returns it), and none
  is invented.
