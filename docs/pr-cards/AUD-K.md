# AUD-K — Cleanup reconciliation + a deletion proof a real project can pass (VMCP-027)

Status: IMPLEMENTED 2026-10-28 (branch `ai/vivienne/aud-k-cleanup-delete-proof`, base main `bb1b132`) — VMCP-027 stays **open** until its live acceptance passes (the stranded 2026-10-28 probe run discharged end-to-end through the fixed cleanup, after release). VMCP-023's closure cleanup leg depends on this card.

**Why this card exists:** after AUD-J's probe, the stranded scratch run could not be cleaned up. Two full `vercel_dev_cleanup` plan → confirm cycles returned `applied` with `confirmed: false` and deleted nothing, and the fallback `vercel_project_delete` refused at the guard ("Could not safely preview or classify the change") — on a project independently read back as completely empty. The deletion half of the rtc lifecycle does not work against real projects. (The same signature appeared at S7, where cleanup's project delete landed *uncertain* and the orphan was deleted from the dashboard.)

## Diagnosis (2026-10-28, live evidence + source + vendored OpenAPI snapshot)

Two defects, both proven:

- **D-A (proven — cleanup can never reconcile a creation intent, so a failed run is uncleanable forever).** Cleanup's apply blocks a run's `project` object while **any** `intent` object in the run is not `cleaned` ("Unresolved provider creation intent exists in this run"). But `deleteExactObject` has **no branch for intents**: an intent falls through to "This resource type requires its own guarded lifecycle before cleanup" and can never transition to `cleaned` through the tool. An intent's outcome is set only on the seed's success path, so any seed that fails after recording a creation intent — the normal failure shape intents exist for — strands its run permanently: the intent blocks the project, and nothing can clear the intent. The design's safety intent (an unresolved creation must be reconciled before teardown) is right; the reconciliation path was never built.
- **D-B (proven — the deletion inventory proof demands fields the provider does not return).** `inspectProjectForDeletion` (shared by `vercel_project_delete` and cleanup's project branch) requires the project record to carry `storageConnections` or `stores` as an array, `crons.definitions` as an array, `hasDeployments` as a boolean, and a present `link`. The vendored snapshot's project schema (98 properties; required: accountId, alias, defaultResourceConfig, deploymentExpiration, directoryListing, id, name, nodeVersion, resourceConfig) contains **neither `storageConnections` nor `stores` at all**, and does not require `link`, `crons` or `hasDeployments`. The inspect therefore throws for real projects generally; the guard surfaces that throw as the classification refusal, and inside cleanup the same throw is what S7 recorded as *uncertain*. The unit fakes model records **with** the invented fields (`stores: []`, `storageConnections: []` in both test files) — the fixture-blindness pattern, fourth instance. There is also no storage or cron list operation in the server's operation table: storage inventory has no provider surface this server can read.

- **D-C (found during this card's implementation, by its own tests)** — an intent-ONLY run (a seed that failed at `projects_create`, leaving exactly one intent object) is refused before cleanup even starts: `targets()` filters intents out, the target list is empty, and the protected-resources guard denies an unidentified write ("The write targets were not identified"). Same finding, third facet: the run shapes a failed seed can leave were never walked through the cleanup contract end to end.

## Scope

**In:**
- **Intent target identification** (`dev-runs.js`): cleanup's `before` derives each intent's write target — the project it concerned (by name for a creation intent, by recorded project id for a deployment intent) — while the private detail is in hand, and `targets()` includes any such target not already identified. The guards evaluate it like any project target: an owner-protected name or id still blocks.
- **Intent reconciliation** (`dev-runs.js`): `deleteExactObject` gains an intent branch. An intent reconciles (`cleaned`) only when its creation is proven to have produced nothing unrecorded: for a `projects_create` intent, the named project is absent (404), or present **and** recorded as this run's project object; for a `deployments_create` intent, the project's complete deployment inventory (the same completeness discipline as the deletion proof) contains no deployment carrying this run's `rtc_run` meta, or every such deployment is recorded as this run's deployment object. An existing-but-unrecorded target returns a blocked reason naming manual reconciliation — cleanup never deletes or ignores an unrecorded resource. An absence that cannot be proven (a provider read fails) throws, landing in the existing uncertain handling. Unknown intent operations keep the existing fallthrough refusal.
- **Ordering**: cleanup's apply processes intent objects before all others (relative order otherwise unchanged), and each outcome updates the in-memory object state, so the project-block check evaluates reconciled statuses within the same pass.
- **A deletion proof a real project can pass** (`project-delete.js`): the storage demand and the `storageConnections` inventory entry are removed (no documented field, no list operation — see the recorded limit below). `link` and `crons` are read as documented-optional: absent or null counts as none; a present `crons` must still carry a `definitions` array or the proof refuses, and a present link object counts as a git connection. `hasDeployments` stays a conservative signal (true ⇒ not empty) but is no longer type-demanded; the scoped, completeness-checked deployment list remains the authoritative deployment proof, as do the domain and env lists. `countComplete` is exported for the reconciliation's reuse.
- **Tests remodeled on the real record**: the project-delete storage-alias and malformed-storage cases (which modeled fields the API never returns) are replaced — a documented-shape project with **no storage fields at all** deletes cleanly; a git-linked record and a cron-carrying record still refuse; store-style wiring is refused through the inventory that actually surfaces it (env vars). The cleanup tests gain the stranded-run shape end-to-end: a failed seed's run (project object + unreconciled deployment intent, deployment inventory empty) cleans fully in one pass; an unrecorded run deployment blocks both intent and project with nothing deleted; a lone `projects_create` intent over a 404 reconciles. Existing cleanup fixtures drop the invented storage fields.
- Register (new finding VMCP-027 with this diagnosis), DECISIONS entry, STATUS entry, TOOL-CATALOG note.

**Out (non-goals):** any weakening of the list-based inventories (deployments/domains/env completeness rules are untouched); auto-deleting or auto-recording an unrecorded resource an intent points at (manual reconciliation stays the answer); the seed's own failure bookkeeping (the intent staying `active` after a failed seed is the correct input — cleanup is where reconciliation belongs); `vercel_project_list`'s one observed `unknown_error` in the same window (undiscriminated; reproduce-or-drop is recorded under VMCP-027, not silently fixed here).

**Recorded limit (storage):** with no documented record field and no list operation, a connected store cannot be inventoried by this server today. The practical tripwire is that store connections wire themselves into a project as environment variables, which the env inventory does prove. If the provider documents a storage inventory surface, the proof should adopt it — a dated amendment to VMCP-027 is the route.

## Acceptance

- **Reconciliation:** against the fakes, the stranded-run shape cleans in one pass (`confirmed: true`, the DELETE dispatched exactly once, intent and project both `cleaned`); the unrecorded-target shape deletes nothing and blocks with the manual-reconciliation reason; the lone project-intent shape reconciles on a 404.
- **Deletion proof:** a documented-shape empty project (no storage fields, optional fields absent) passes the inspect and deletes with the existing double-inspection discipline; git-linked, cron-carrying, env-carrying, domain-carrying and deployment-carrying projects still refuse or preview as not eligible; `hasDeployments: true` still denies even with an empty deployment page.
- **No regressions:** `npm run check` green at the committed range; the full unit suite passes (observed: **1043 tests, 118 files, exit 0** — 3 reconciliation tests added; the two storage-model deletion tests and the missing-link test replaced by two documented-shape tests).
- **Live acceptance (post-release, closes VMCP-027 and VMCP-023's cleanup leg):** `vercel_dev_cleanup` on the stranded probe run (its scratch project read back empty, its deployment intent unreconciled) completes with `confirmed: true`, the project verified gone through the MCP and independently. Until it passes, VMCP-027 stays open.
