# E-1 — project environment metadata and guarded value workflows

Status: IN_PROGRESS, candidate PR #174. Approved design: docs/designs/BATCH-E.md. Dependency: D-1 implemented; this read-only slice does not depend on incomplete D-3 writes. Baseline: 9f9be99d8baf2c9d20fc7fb50fa844a0f58e4684.
Budget: no paid provider calls or writes; no schema migrations.

## Current substantive slice: three native read capabilities

`vercel_env_list`, `vercel_env_get`, `vercel_env_export_names` resolve an exact server-selected project from the saved encrypted account, independently read `projects_get`, then use documented pinned GET `/v10/projects/{idOrName}/env` and GET `/v1/projects/{idOrName}/env/{id}`. The list always sends `decrypt=false`; get may receive provider fields but returns an allowlisted metadata projection only. All paths strip values of *every* type (plain, encrypted, sensitive, secret or system), including untrusted comment and metadata fields. No generic full-detail bypass, handles containing values, audit output or direct source dump. A metadata-only `.env.example` key export must contain assignments without values.

A returned variable with contradictory project ID, malformed key or ID, duplicate IDs/keys or unsafe field type fails closed. Pagination must describe boundedness honestly and never claim the complete provider inventory without a trustworthy cursor. Keys and targets are bounded/sanitized. No cross-project/team requests.

## Provider create envelope correction (#179)

Vercel's documented POST response may wrap created environment metadata under `created` and include per-item failures even on HTTP success. Single-create and Config copy both now normalize IDs from direct/wrapped success safely and refuse partial/mismatched success without leaking provider fields. Such ambiguity is an `outcome_unknown` requiring a readback, never a blind retry.

## Bounded E-1 provider batches (#180 candidate)

Two independent complete guarded workflows: create-only 2–10 new keys via one POST and delete 2–10 exact ID/key/revision variables from all their targets via one DELETE batch. Both use single Vercel requests (not a guarantee of provider transaction atomicity), typed input, replay, owner-guarded confirmation and production classification, fresh before-dispatch evidence and independent per-item readback. Secret bytes or raw error fields never appear in output. Mixed/partial provider responses remain unknown and must be reconciled, not retried automatically. The existing deployment never changes; a separately authorized redeploy is required for new environment values to take effect. Remaining acceptance: checked production release and approved disposable provider fixture, plus expanded branch/cross-project Config copy.

## Exact preview-branch Config copy (candidate #184)

The approved single-project Config copy workflow extends to explicitly selected preview Git branches. Source and destination branches are optional, strongly validated and legal only for preview targets; the source's `gitBranch`, ID/key/revision, nonproduction targets and safe Config value are independently rechecked before dispatch. Preview branches may be copied to a distinct ordinary or preview-branch destination; destination creation uses `gitBranch` only when authorized, with create-only semantics and no automatic deployment. The independently fetched created row must match the requested destination branch, target and value before `confirmed:true`; mismatches never become success. Source and destination may not be the same project/key/target/branch. Secrets, custom environments, cross-project copies, branch traversal, changed state and credential-like Config values fail closed. Full source/destination values/digests never leave the server. Real acceptance needs a released source and an owner-authorized disposable preview fixture; no provider writes were performed for this code change.

## Same-team cross-project Config copy (candidate #185)

An optional exact `destinationProject` extends the approved Config-only copy. Copying to another project requires `outsideApp:true` and stored *team-wide* authority (project-scoped credentials cannot perform it). Both source and destination must be independently resolved through Vercel under the same team before preview and immediately prior to dispatch. Protection and application guards cover both projects, and production destination continues to require the original production gate. The single create-only POST writes to the independently verified destination; a separate scoped GET from that project must show the intended key, target, exact optional preview branch and value equality. A changed/foreign destination, missing outside-app intent, inaccessible project, unsafe value, Secret source, custom environments, replay conflict, ambiguous POST and mismatched readback never become confirmed success. The source value, its digest and provider rows remain hidden from outputs, durable replay and audits. Two owner-authorized disposable projects and exact deployed-source evidence are necessary for external acceptance; no live provider write is part of this PR.
