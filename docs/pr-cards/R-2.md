## Drift check B — current native MCP OAuth client compatibility (pre-implementation)

2026-10-19 verified `src/core/oauth-handlers.js` accepts only `client_secret_post` in dynamic registration, and `src/db.js` requires a stored secret for all OAuth clients. This excludes public desktop/mobile clients that legitimately cannot safeguard a confidential secret. The 2026-07-28 MCP authorization specification requires appropriate OAuth security for **both public and confidential** clients, and strong authorization-code PKCE S256: https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2026-07-28/basic/authorization/index.mdx.

Additive R-2 direct OAuth criteria before code:
- Retain unchanged existing confidential clients and their hashed client secrets, code/refresh binding, expiry, revocation and account selection; do not migrate or invalidate any current owner connection.
- Permit explicitly registered public clients using `token_endpoint_auth_method=none`, WITHOUT returning or storing a fabricated client secret; require S256 PKCE, exact registered redirect and protected MCP resource for every code. Treat client ID alone as non-secret, refuse public token calls presenting `client_secret`.
- Refresh token rotation must remain atomically one-time, bound to original client ID; wrong client/unknown/revoked/used/expired credentials fail. Neither public registration nor public caller arguments grant team, scope, write, spending or production rights.
- Prove positive confidential and public OAuth code/refresh flows, denied wrong/missing PKCE, wrong client/redirect, secret-mode confusion, metadata truth and real disposable-Postgres behavior. Record external client compatibility as pending until independently tested.
- Keep public OAuth registration subject to ordinary deployment policies; do not publish a directory listing, broaden provider credentials or contact customers.
