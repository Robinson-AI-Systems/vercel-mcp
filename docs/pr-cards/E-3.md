## Cohesive PR candidate: safe listing, create, item patch and store deletion

- `vercel_globalconfig_list` is a read-only selected-team `GET /v1/global-config` of bounded projected store identities, slugs, item counts, size and **only verified connected project identifiers**. Missing provider owner/link metadata are represented as unknown, not empty. Full-completeness is claimed only when a native provider pagination terminator is explicitly witnessed; max 20 results, no tokens.
- `vercel_globalconfig_list_items` re-verifies the exact selected store using `GET /v1/global-config/{edgeConfigId}`, then fetches items from `GET /v1/global-config/{edgeConfigId}/items`. Returns at most 20 safe key/data projections and marks completeness unverified; credential-shaped config values are redacted by canonical `compact`. No raw provider rows, tokens or auth fields returned.
- `vercel_globalconfig_create` uses `defineWrite` to create an empty, initially unconnected store using `POST /v1/global-config` only for a verified selected team. It requires exact safe slug, an explicitly complete selected-team inventory to rule out existing names, separate confirmed preview/owner/app/protected/replay preflight, before-dispatch inventory recheck, safe create result, and independent GET readback. A missing link inventory is *unknown*, not verified unlinked. No tokens/items/links or deployments are created.
- Source additions: common bounded metadata/identity helpers, explicit allowlisted registry and pinned vendor operations, security and HTTP fixture tests. Values, tokens and raw provider bodies must never appear in result/audit/replay.
- **Evidence status:** implementation and fake-provider tests are not provider acceptance. Exact-head CI, code review and merge must pass. Native TEST list/items/create with owner-scoped disposable fixture remains pending a checked live source deployment; never use a protected or production resource without independent owner approval.
- **E-3 implementation completion candidate after this subsequent PR:** one-time read-token creation and version-specific backup restore are now implemented together with E-4's adjacent token inventory/revocation. External acceptance remains pending. Next PR in approved order should complete adjacent independent slices while preserving the full security gates and evidence separation.

## Safety and acceptance

Store item writes are effectively **production** if any connected project reads the store live, even if connection.mode is PREVIEW. Provider response must prove every connection and resource ownership. Do not infer a store has no consumers from missing `connectedProjects` or from a short/paginated list. Restore requires backup/version identity and an item diff preview; token creation uses the owner's one-time setup page and no return of token contents.

Tests for this first candidate assert exact official request paths, secret-shaped response redaction, scoped team, missing/duplicate rows, incomplete pagination, read-only protections, protected account, no-confirm/dryRun, concurrent slug collision, and zero unintended provider mutations.

## Source candidate for E-3 final token/backup slices

- `vercel_globalconfig_create_token` issues the exact official v1 token POST,
  full-profile only. The selected team, exact store ID/slug/revision,
  linked-project production classification, token list identity, guarded access
  widening, owner confirmation, protected/app guard and replay must pass.
  The provider token string is retained **only inside the server** during
  immediate AES-GCM encrypted one-time owner-vault issuance; MCP gets an
  authenticated owner-reveal UUID (expires within 10 minutes), never a bearer.
  Missing encryption key/secret vault fails before POST. Failed uncertain
  provider issuance requires readback and owner cleanup, never blind replay.
- `vercel_globalconfig_restore_backup` pins an exact backup version, reads
  target and backup contents only inside the server, previews names of every
  added/removed/updated item (not values), verifies the current item count
  and selected-project team ownership, and rechecks the diff immediately
  before restore POST. Connected stores are production. Readback compares
  exact restored item values server-side and reports boolean equality only.
- No current Vercel provider mutation, owner grant, token, or production
  activation was used. Synthetic request/readback and one-time encrypted
  vault tests plus exact-head CI are required; native TEST acceptance and
  checked release are independent pending queue items.
