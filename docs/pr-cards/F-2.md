## Build contract

1. **Operations** (pinned snapshot paths; added to
   `src/vercel/operations.js`): `firewall_config_get` (GET
   /v1/security/firewall/config), `firewall_config_get_version` (GET
   …/config/{configVersion}), `firewall_config_patch` (PATCH
   …/config), `firewall_config_activate` (POST
   …/config/{configVersion}/activate), `firewall_attack_status` (GET
   /v1/security/firewall/attack-status), `attack_mode_update` (POST
   /v1/security/attack-mode), `firewall_events_list` (GET
   /v1/security/firewall/events). The config DELETE operation is NOT
   registered — the catalog has no delete-version tool (dossier §2.4).

2. **The PATCH oneOf cannot be machine-validated** (dossier §4.1, proven
   with the repo's own AJV settings: documented bodies match two branches
   or the wrong branch; branch descriptions are shifted one position from
   their action enums). Disposition: `firewall_config_patch` is the one
   operation exempt from `validateRequest`; bodies are constructed
   strictly per the documented branch shapes (enums + value shapes) and
   pinned byte-exact in fake-provider tests. Every other F-2 operation
   validates normally. The shared normalization machinery is NOT extended
   inside Batch F; the snapshot/normalization follow-up is recorded for
   the coordinator.

3. **Diffs in words** (design F4): every write reads the active
   configuration in `before()`, renders the change in plain words for the
   preview ("Deny requests whose path equals /wp-admin"), captures the
   active version, and declares the inverse
   `{tool: 'vercel_firewall_restore_version', project, version: <previous
   active version>}`. Apply re-reads and refuses on drift (active version
   moved, or the target rule/IP entry changed); verify re-reads and
   confirms the change in the read-back configuration (active first, then
   draft — the verify result says which one carries it).

4. **Rules**: the public condition surface is one condition group
   (`conditions: [{type, op, value, key?, neg?}]`) with the contract's
   enums; the mitigate action is one of allow/bypass/challenge/deny/log/
   rate_limit/redirect with the contract's rateLimit/redirect shapes.
   `update_rule` merges the caller's changes over the current rule and
   sends the full documented `rules.update` value; `remove_rule` sends
   `{action: 'rules.remove', id}`. Rule identity is the provider id;
   unknown ids refuse in `before()` naming the rule list size.

5. **Managed rule sets**: one call sets one ruleset — the five
   `managedRules` keys route to `managedRules.update`, the eleven CRS
   keys to `crs.update`, each `{action, id, value: {active, action?}}`
   with the family's own action enum (managed: challenge/deny/log; CRS:
   deny/log). The catalog marks the tool PR with no `$` (dossier §4.5:
   the design's §5.2 $-suggestion is rejected — no per-call price exists
   in the contract, and a `$` declaration would fail check-writes
   against the catalog); a plan-gated provider refusal surfaces as a
   classified error with its remedy.

6. **IP blocks**: `block_ip` sends `ip.insert` (hostname defaults to the
   IP text; action deny by default, or challenge/bypass/log);
   `unblock_ip` finds the entry by IP in the active configuration and
   sends `ip.remove` with its id. IPv4/CIDR only, as with trusted IPs.

7. **Attack mode** (design F4 + dossier §2.6): turning on REQUIRES
   `durationMinutes` (5–1440; the 24 h product cap is a refusal, not a
   clamp) and sends `{projectId, attackModeEnabled: true,
   attackModeActiveUntil: <epoch ms>}`; turning off sends the two-field
   branch. Verify reads attack status back (else confirmed: null — the
   status contract's opaque branch cannot prove state).

8. **Events**: aggregated provider summaries projected to the documented
   fields only, bounded `limit` (default 20, max 50), `hasMore` reported;
   never a raw provider row.

9. **Catalog and pins**: registry/front-door/production-approval pins
   move by eleven (reads +3/+3/+3, writes +8 full, +3 everyday); catalog
   header counts recomputed at build time (siblings merge in parallel);
   STATUS bullet in this PR. No database change.

## Build addendum (2026-10-30, during the build)

Three further snapshot defects were proven against the repo's own validator
while building, each handled with a narrow, commented exemption in
`src/vercel/openapi-validation.js` following the existing
`sandbox_command_run` precedent:

1. The snapshot declares **no parameters at all** for
   `GET /v1/security/firewall/config` and no `projectId` for the activate
   POST, although the live REST reference requires `projectId` on both (the
   PATCH and version GET on the same paths declare it). The exemption
   permits exactly that one parameter for those two operations.
2. The attack-mode enabling body double-matches its oneOf (the two-field
   branch does not forbid `attackModeActiveUntil`), so body validation is
   skipped only for the documented enabling shape; the disabling body keeps
   full validation.
3. The firewall PATCH body exemption from the dossier (branch overlap) is
   implemented in the same place, because the client validates every
   request internally — there is no caller-side opt-out.

Also proven while fixturing: the config object requires a `changes` array,
and provider rule records carry `rateLimit`/`redirect`/`actionDuration` as
null when unused — the tools accept and re-emit that shape.
