# AUD-K2 — Door-1 team installs enroll through an installation-aware probe (VMCP-026 / A-1)

**Naming:** this is the audit pipeline's **AUD-K** packet (the installation-probe fix filed by the VMCP-026 acceptance draft and specified by the contract dossier of 2026-10-30). It is filed in-repo as AUD-K2 because `docs/pr-cards/AUD-K.md` is already the VMCP-027 cleanup-reconciliation card; nothing about that card changes here.

**Baseline inspected:** main `42e6f79` (AUD-Y); rebased onto `c894606` (the 2026-10-30 acceptance filings, #276) before push — STATUS-bullet ordering only. Predecessor: AUD-I S1–S5 (the Door-1 build this card completes the enrollment half of).

**Conviction (live, 2026-10-30, acceptance A-1).** A Door-1 team install completes on Vercel's side, the callback exchanges the code successfully, and enrollment then throws "Could not confirm the token team visibility with Vercel (HTTP 403)" — nothing is stored, so no Tier-1 team seat can ever be created. Root cause, proven from the documented contract before any code (dossier, shape map rows 1–6): team installs enrolled through the standard pasted-token probe, whose load-bearing legs are `user_get` + `teams_list` + `projects_list`. The per-scope endpoint map grants an installation token no teams-list endpoint under any scope, and live behaviour agrees (403 on the teams leg). Two sibling defects ride the same root: the tests faked the impossible call (the team-install fixture answered `GET /v2/teams` with the team, so the suite was green against a fake the contract contradicts), and `recheckStoredToken` routed integration team rows through the same probe, so every Door-1 seat would have failed its first recheck forever.

**Fix (per the dossier's remodelled flow, §5).**
- **New operation** `integrations_configuration_get` — `GET /v1/integrations/configuration/{id}`, team-scoped (the client attaches the install's `teamId`, which the endpoint declares), verified against the pinned snapshot before adding, per the operation table's own rule.
- **`probeInstallationToken`** (tokens.js): builds the client exactly as the existing probes do, then (1) reads the installation's own configuration and shape-gates it on the documented required set; hard checks — the configuration belongs to *this* integration (`integrationId` vs the server's configured client id) and to the exchanged team (`teamId` and `ownerId`); dead checks — `deletedAt`, `disabledAt` (AUD-I S5 wording verbatim), `status` `uninstalled`/`suspended` (absent status takes the documented `ready` default); the installer cross-check (`config.userId` vs the exchange's `user_id`) is recorded, never a refusal ground. (2) Derives scope from the configuration alone: all-projects → `team`; a grant limited to exactly one project → `project` with that project; limited to more than one → refused (a stored row covers one team or one project; recording `team` would overstate the credential's reach); limited to none → refused. Never `full`; no broad-visibility gate exists on this path because a configuration-bounded token cannot see a second team. (3) Proves function with the existing bounded `projects_list` read, cross-checked against the granted set (a visible project outside the grant, or the single granted project invisible, refuses as a record/reach disagreement). (4) Labels the row from the single-team read (`teams_get`, team scope), best-effort with the team ID as its own label on any failure — the configuration's `slug` is the *integration's* and is never used as a team label.
- **`storeInstallationToken`** mirrors the S1b sibling: same upsert row shape as `storeToken`, probe record carrying the existing integration provenance plus the configuration-derived evidence (`grantedScopes`, `projectSelection`, `configurationStatus`, `installerMatchesConfiguration`) and the standing honest `scopeVerified: false`.
- **`enrollInstallation`**'s team branch calls it instead of `storeToken`; personal installs are untouched. The probe's identity inputs come from the validated exchange response; the callback additionally cross-checks the redirect's `configurationId`/`teamId` against the exchange and refuses a mismatch before any probe call (dossier §5 step 0).
- **`recheckStoredToken`** routes `source: 'integration'` team rows through the same probe (inputs rebuilt from the stored installation id + the configured integration client id), exactly as it already special-cases personal rows. Pasted-token and personal routing are byte-identical to before.
- **Every refusal classifies per IN-18** (dossier §6): configuration 401 (dead credential — reinstall), bare 403 (missing integration-configuration read grant — console grant + confirm + reinstall), 403 with the documented `integration_configuration_disabled` code (the existing S5 message, reused verbatim), 404/410 (installation gone — reinstall), shape violation, wrong integration, wrong team, disabled/deleted/suspended, multi-project and zero-project grants, projects-leg 403 (missing project read grant), grant/reach disagreement, storage (unchanged). Nothing is stored on any refusal.

**Tests — the fixture blindness is the fix's other half.** `tests/unit/integration-install.test.js` is remodelled on the dossier's fake spec (§7): the team fixture's `GET /v2/teams` success fake is **deleted** and replaced by a configuration object copied field-for-field from the documented schema (including nullable `teamId`, the prefixed `scopes` array, `projectSelection`/`projects`, and the integration-slug trap field) plus the single-team label read; the user read remains only so the enrollment test can assert the probe never consults it (and never the teams list). New coverage: every refusal branch above with zero stored rows; the disabled-envelope case flows through the client's real envelope parsing so the S5 classification is what is exercised; single-project enrollment as a project row; the label-failure fallback; the absent-status default; a stored integration team seat rechecking through the configuration read with the same no-teams-list/no-user call-set assertion; and the callback cross-check (agreement completes; either mismatch refuses before any probe call). Personal fixtures and assertions are unchanged.

**Drift resolution (checklist B).** The tool surface does not change: AUD-K2 adds an internal provider operation and reroutes enrollment/recheck internals — no tool is added, removed or re-shaped, so `docs/TOOL-CATALOG.md` is not touched (the docs check requires it only when `src/tools/` changes). This PR changes `docs/STATUS.md` and this card, satisfying the enforced minimum. The connect-page copy item in the dossier (§8) needs no change: S2's shipped copy already tells the user, in plain words, that Vercel's own screens are where they pick the team and the projects; no documented install URL carries a target team, and the install URL itself is operator configuration, unchanged here.

**Acceptance.** Unit-proven in this packet (the remodeled suite plus the full repo check at the exact head — counts recorded in the PR). **Live closure of VMCP-026's A-1 rides the release:** after the nightly promotion, ONE confirmation install against the scratch fixture team must enroll and read back (the dossier's reserved confirmation probe — confirmation, not diagnosis), and A-2/A-4/A-5/A-9/A-11/A-12's Tier-1 legs unblock behind it. VMCP-026 stays open until those pass.

**Builder guardrails (binding, restated).** Tests use fakes only; no real token, no live call, no enrollment attempt in this card. No secret or real team/project/configuration ID appears in the change — fixtures use fake-shaped values only. Builder rules live in this card and the dossier, never in runtime code.
