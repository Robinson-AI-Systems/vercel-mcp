# AUD-I — "Log in with Vercel": Integrations connect tier, dynamic box choice, explicit god-mode tier (VMCP-026 / IN-16)

Status: CARDED 2026-10-28 (design + acceptance filed ahead of the build, S5 pattern) — build starts when VMCP-023 closes, per the owner's sequencing ruling 2026-10-28 (this build next; the narrowed remainders VMCP-003/011/016 and VMCP-025 follow). **Build underway 2026-10-29: slice S1 merged-ready — the Door 1 backend (install code exchange under the documented contract + team-install enrollment through the probe/store path, installation identity + declared box recorded; callback at /api/vercel/integration). Personal-account installs enroll through the user-keyed probe as of slice S1b (merged-ready 2026-10-29; DECISIONS). Remaining slice: S5 revocation honesty + posture.** VMCP-026 stays **open** until its acceptance probes pass live. Design addenda the same day: the two-layer box model (granted ceiling / working box); the **research verdict that corrected this card's mechanism** — Tier 1 is the Vercel **Integrations** connect flow, not Sign in with Vercel (see Step 0); the owner's **account-layer correction** — Account-wide is a tier capability at the account layer, never a sum of team installs (see "Account-wide is a layer, not a sum"); and the **connection-page design** — one page, two doors, mirroring the GitHub MCP (see "The one flow"); and the owner's **simplification ruling** — setup shrinks to the door choice (+ paste at Door 2). **IN-17 and IN-18 (both ruled 2026-10-28, governing) supersede the switchboard half of that ruling**: no inside switchboard is built; god mode = everything ON; the posture self-report survives as information; IN-18's doctrine (build for full access, never pre-stop, legible refusals with remedies) governs every capability question in this card.

**Why this card exists:** IN-16 (owner direction, 2026-10-28) ruled that when development and testing are done, end-user onboarding becomes a normal sign-in: the user logs into THEIR OWN Vercel account, the way the GitHub MCP links a GitHub account — a connection page, the provider authenticates them, and the server receives a scoped credential without the user ever handling a raw key. The same day's addenda completed the shape: the SAME two-tier authority as the GitHub MCP (standard login tier + owner-chosen god mode), and a **dynamic box choice at sign-in** (the user picks one project / a team / the whole account, in plain words, and the backing credential changes to match). Current state, verified in the shipped code: enrollment is token-paste only (`src/vercel/setup.js`, "Add or rotate a Vercel token"); no Vercel OAuth sign-in exists anywhere in the product.

## Design

### Step 0 — platform verification: ANSWERED by research (2026-10-28); build-time checks narrowed

This card was originally written against an assumption — that "Sign in with Vercel" could power the login tier — and its Step 0 existed to test exactly that. The test ran early, as deep research against Vercel's current official documentation, and **the assumption failed**. The verdict, which now governs this card:

- **Sign in with Vercel is GA for identity only** (scopes `openid` / `profile` / `email` / `offline_access`). The per-resource API permissions that would let its token act on teams/projects are **still private beta** (scopes-and-permissions page dated 2026-02-26), and Vercel staff stated (~Oct 2026, community reply) they are **not adding new teams to the beta**. It cannot power this product today. It remains the roadmap upgrade: when those permissions GA, this same design rides Sign in with Vercel instead — the two-layer box model and the plain-words flow do not change.
- **The only GA OAuth path to an API token is the Integrations flow** — strictly **one team (or one personal account) per installation**; one grant cannot span teams. The user flow is pure clicks (install page → select projects → Install); the server exchanges a one-time code for a **long-lived** token bound to the installer — it is **disabled if the installer loses team access** (and auto-removed after 30 days if not re-enabled). The user never creates, copies or pastes a token in this flow. Within a team, adding projects later is a dashboard **Manage Access** step — no reinstall. A different team is a **new install**. An integration token **can create projects** inside its granted scopes; its **team scope is read-only** (no team creation, no member management) and no scope covers minting tokens — that ceiling is documented, and this card treats it as evidenced fact, not as a defect to route around.
- **Only manual API tokens have a Full Account scope** ("personal account and every team you belong to"). No OAuth route to whole-account exists today — so the god-mode tier stays token enrollment, exactly as IN-16's addendum filed it.

What remains for build time (verification, not research): the integration must exist and be installable — created in the Integrations Console as a **connectable account** integration with this server's redirect URL and the declared API scopes, through Vercel's review/approval or sharing path as the docs require; the exact exchange-response fields (`teamId`, `configurationId`) and webhook needs are confirmed against the docs at build time and cited by the test fakes. If any of those mechanics have changed since 2026-10-28, the card is amended with the new evidence before code follows it — the stop-and-return discipline stands.

### The one flow — one connection page, two doors (owner design, 2026-10-28)

Mirror the GitHub MCP's connection process: **one connection page, two doors.**

**Door 1 (the default, easy door):** sign in / install via the Integrations flow → team seats. No token ever touches the user's hands.

**Door 2 (account-wide):** offered in plain words on the same page — *"Want account-wide control?"* — a guided token walk-through, GitHub-style (below).

Whichever door, the flow is:

1. **Pick your box** — one project / a team / the whole account — each with what it lets the agent reach, stated plainly at the moment of choice. The box routes the user to the door that can grant it (Project/Team → Door 1; Account-wide → Door 2).
2. **The credential follows the choice** (mapping below). On Door 1 the user picks the team and the projects **on Vercel's own install pages**; the server receives the installation's token from the code exchange and **stamps the working box from the user's plain-words pick, enforced per call**. The user is never asked twice for the same decision, and never silently re-boxed.
3. **The connection binds as today** — the existing consent machinery (account, mode, profile, listing) completes the connection; the standard tier lands on the server's standard profiles, where the restraint lives (the integration credential is broad inside its installation; IN-16 addendum).

### Door 2 in detail — the guided token walk-through

A button on the connection page opens Vercel's Account Tokens page (`https://vercel.com/account/tokens`), and **our page shows the short plain steps beside the paste box**:

1. Name it anything.
2. Scope: **Full Account**.
3. Expiration: **your choice — including No Expiration** (IN-04: the key owner chooses; the server's duty is to warn ahead, never to choose for them).
4. Create → copy the token (it is shown **only once**) → paste it here.

On paste, the server **probes the token and reads its scope back to the user — confirming "Account-wide" — before the seat activates**, with the declared-box/probe honesty of the next sections intact (where the probe's visibility heuristic cannot fully prove the scope, that caveat is shown, not smoothed over). If a narrower token is pasted at this door, the read-back names its actual scope and the seat activates as *that* box, plainly labeled — never as account-wide by courtesy. After enrollment, the connection's own pre-existing profile choice (the user's setting, made at consent) applies — and in god mode the posture defaults to full: **everything on** (IN-17), because Vercel tokens carry no per-permission checkboxes and this product does not invent a restraint layer of its own (IN-18).

**Setup at this door is exactly that — nothing more (owner simplification ruling, 2026-10-28).** A Vercel token carries no permissions to choose, so Door 2 setup is: the guided link, the plain steps, the paste, the probe, the confirmation. **No permission UI, no profile pick, nothing else at setup for the token door.** Profiles and capability control are not setup questions; they live inside, after connection (see "Control lives inside").

**Verified constraint (Vercel docs, access-tokens page updated 2026-09-08, read 2026-10-28):** Vercel documents **no URL pre-fill** for the tokens page — unlike GitHub, the link cannot land with the scope pre-checked. The mirror is therefore **guided steps, not a pre-set form; do not fake a prefill** (no look-alike parameters, no implying the page was pre-answered). Two more facts from the same page shape the implementation: the token value shows only once at creation (copy-then-paste *is* the flow), and Full Account tokens still take a `teamId` per target team on API calls — **the server handles that invisibly**; the user never sees team plumbing.

### Box → credential mapping

| Box (plain words) | Credential | Account record |
|---|---|---|
| One project | Tier 1 **integration install** on the containing team (projects selected at install, or all projects); the user names the project and the server pins the working box to it | Existing `team/project` key; reach enforced per call by our machinery, corroborated by the install's project set |
| A team | Tier 1 **integration install** on the chosen team (or on the user's personal account — an installation with no team) | Existing `team` key (personal installs key honestly as their own account record) |
| The whole account | **Tier 2 token enrollment** — a full-account token behind the existing IN-04 explicit checkbox | Existing `team` key with the full-account credential enrolled |

Whole account routes to the token tier because no OAuth grant spans teams — whole-account reach is a manual-token property, per the research verdict. The flow says so in plain words at the choice — *why* this box uses a token — never a silent tier switch. **Additional teams are additional installs:** the agent offers them as the user needs them ("Want me to reach Team B too? One install, two minutes") — guided clicks, never a token errand.

### Account-wide is a layer, not a sum (owner correction, 2026-10-28)

The plain-words box list is exactly three — **Project / Team / Account-wide** — and the third is a *tier capability*, not a pile of the second. **Account-wide means authority at the account layer:** switching between teams and projects freely, **creating teams**, account-level settings and actions, and acting on a team that does not exist yet (by creating it). Today only the Full Account token grants that layer, so Account-wide is labeled **token-only** in the product until Vercel's OAuth permissions GA.

A pile of per-team installs is **not** account-wide control, and the product must never present it as such — not in the connection page copy, not in the self-description, not in agent-facing summaries. Team seats, however many accumulate, cannot create a new team, cannot touch account-level settings, and cannot act on a team that doesn't exist yet. Accumulated reach is reported as what it is: the list of installed teams. The owner's own god-mode connection (full-account token) is the **account-wide reference implementation** — the thing the label means, against which any future OAuth route to the account layer is measured.

**Account-level asks from a team seat:** when a user on a team seat (a Tier 1 install, or a team-scoped token) asks for an account-layer action — create a team, change account-level settings, act where no team exists yet — the assistant says plainly that this seat can't reach the account layer and offers the token tier as the route to that power. It never silently simulates account-wide by bundling installs, and never dissolves the answer into a generic permission error.

### The declared box is the record

The account stores the user's **declared box** (the plain-words choice) alongside the existing probe result. `vercel_whoami` shows both: declared box, probed scope, mode, profile. The probe remains corroboration with its honesty intact (`scopeVerified: false` — REST reads cannot prove a token's complete privilege set; the recorded label is a visibility heuristic, e.g. a single-team owner's full-account token can probe as `team`). A probe showing **broader** than the declared box surfaces a plain warning at enrollment time; a probe showing narrower states plainly that the credential reaches less than the box promises. Neither is silently adjusted. (The declared box is the *initial* selection — the next section makes it a setting, not a sentence.)

### The box is two layers: granted ceiling + working box (owner addendum, 2026-10-28)

**One connect pattern serves every box.** The box picked at connect time is the initial selection, not a permanent binding. Tier 1 installs are per team by platform rule (research verdict), so a user's ceilings **accumulate** — one install per team they want reachable, each one the same two minutes of clicks, offered by the agent when the need arises. **Membership, not ownership, is the fence:** a user who belongs to a team — any role — can install on that team and point a connection at it, and their reach inside it is exactly their role's reach, enforced by their credential (an integration token also dies with the installer's team access — the platform enforces the same fence). The server never exceeds the credential behind the connection; it also never demands ownership the platform doesn't.

The box is modeled as two layers:

- **The granted ceiling** — the widest credential the user has given the server, **per team**: that team's integration install, bounded inside the team by the install's granted project set (all projects, or the selected set); or, on Tier 2, an enrolled token's scope. The ceiling is the *grant*.
- **The working box** — a per-connection, server-side setting. It can be **narrowed freely** at any time (a team credential, a project working box for safe testing) and **widened instantly up to the granted ceiling** — flipped by the agent through a tool, on the user's say-so, with **no re-login**. Every flip is journaled like every other connection change. Restraint is a *setting*; the ceiling is the grant.

**Widening has exactly three rungs, and the agent names the right one:** (1) inside the granted ceiling — instant, on the word; (2) a project in an *installed* team that the install didn't grant — a one-time **Manage Access** step on Vercel's dashboard (no reinstall), which the agent names and walks through; (3) a team never installed, or the whole account on a Tier-1-only setup — a **new install** (clicks), or the token tier for whole-account, respectively. In rungs 2 and 3 the agent says so plainly and walks the user through the one-time step — never silently fail, never pretend the flip happened, never narrow the answer into a generic error.

Copy consequence, binding on the enrollment and OAuth surfaces this card builds: because the working box can always be narrowed afterward, the copy **encourages granting the widest ceiling the user is comfortable with**, disclosed in plain words at the grant moment — what it reaches, and that narrowing afterward is free and instant.

**The agent must know and say.** The connection's self-description (`vercel_whoami` or its successor) reports, in plain language any agent can relay verbatim: the current **working box**, the **granted ceiling per installed team** (including each install's project reach — all projects, or the selected set), **which flips are instant**, and **which flips need which one-time step** (Manage Access, a new install, or the token tier) — so a freshly connected agent proactively tells its user: *"You're pointed at one project; you can widen to the rest of this team, just say the word — and if you want Team B as well, that's one install, two minutes"* (naming the step that is actually true). This is a requirement on the output text, not a hope about agent behavior.

Tool surface: the flip is an agent-called tool. It ships reachable through the catalog (`vercel_call`) at minimum; promotion into the front door happens only if the OP-1 budget (5,000 tokens; 4,670 at the last measurement) fits it, measured at build time — this card does not pre-spend that budget.

### Control lives inside — as information, not restraint (IN-17 supersedes the switchboard, 2026-10-28)

This section originally designed a server-side capability switchboard. **IN-17 (governing, 2026-10-28) dropped that build**: the product is not engineered toward restriction — **the door choice IS the safety model** (Door 1 per-team seats for safety-seekers; god mode = everything ON), and engineering effort redirects to capability and coverage under IN-18. What survives of this section:

- **The posture self-report — as information.** The connection's self-description (`vercel_whoami` or its successor) reports in plain words: what credential width it holds, what capabilities are available to it, its box state (per the sections above), and the state of the user's own pre-existing settings. Agents surface this so the user always knows their posture; nothing in the report gates anything.
- **Pre-existing user-owned settings stand, defaulting ON in god mode** — the IN-09 production switch is the type case: it is the *user's* switch, flippable by their agent on their word (VMCP-002, closed live), never a product-imposed gate. In god mode it defaults ON.
- **Cost/effect previews + the journal** remain the transparency layer: disclose → execute on the word → journal → verify.
- **IN-18 governs every capability question in this build:** build for full access, never pre-stop an attempt (Vercel owns plan/usage/budget/role gating), and on a platform refusal classify WHY in plain words (plan, usage limit, budget, role, scope) with the remedy attached — execute the fix on the user's word where the API exposes it, point to the dashboard honestly where it doesn't.
- The honest limit that survives unchanged: a credential's reach is what Vercel granted it; the platform-side kill switch is the user's — delete the token at Vercel, or uninstall the integration.

### The Tier 1 platform ceiling, evidenced (not a defect)

An integration credential's hard ceiling is the integration's declared scope list, and the research documents what sits outside it: **no team creation** (team scope is read-only), **no member management**, **no minting of user tokens**, and env-var access at read/write granularity only (no read-only env tier). Those missing operations are not a random gap list — they are the boundary of the **account layer** (see "Account-wide is a layer, not a sum" above): a team seat is powerful *inside* its team and structurally blind above it. On Tier 1 connections the product must not promise those operations — tool surfaces and copy state the ceiling where a user would meet it, the same evidenced-ceiling discipline the audit applies everywhere (D9): the capability ceiling is what the user can do *through this credential class*, and the Tier 2 token tier remains the route when a user needs the operations only a user token can do. The integration's declared scopes are chosen to cover the product's documented tool surface as broadly as the scope list allows; any tool whose endpoint sits outside every declarable scope is named in the implementation PR as Tier-2-only, with the scope evidence cited.

### Tier 2 made explicit (no behavior change underneath)

The setup page's enrollment section is re-presented in plain words as the **god-mode tier**: what it is (a token you create with everything on), what it unlocks, the scope boxes, the expiry choice **including never** (IN-04: the key owner's choice; the server's duty is warn-ahead — the 14-day warning already in `vercel_whoami` / `vercel_admin_overview`), and the explicit broader-account checkbox as the deliberate act it is. Probe, storage, encryption and journaling are unchanged. The simplification ruling applies here too: this section explains and enrolls — it does not grow control UI; what control exists lives in the user's own settings and the posture report (IN-17).

### Revocation from both sides

- **In-product:** disconnecting an account deletes its stored credential (journaled like every account change); connections bound to it fail honestly afterward.
- **At Vercel:** revoking the token or uninstalling the integration makes the credential dead; the next use fails honestly and the account's posture surfaces it as dead — no silent success, no stale "connected" claim.
- **By the platform:** an integration token is disabled when its installer loses access to the team (auto-removed after 30 days if not re-enabled). The server cannot prevent that; it must *notice* it — the next call fails honestly and the posture names the cause class (installer no longer on the team) rather than reporting a generic dead credential.

### Operator secrets

The integration's client credentials are server environment values set by the operator (the `ADMIN_PASSPHRASE` pattern): never in the repo, never in chat, never returned by any tool. The integration's redirect URL is this server's own origin.

## Scope

**In:** the research verdict as this card's basis (Step 0 above) + build-time confirmation of the integration mechanics; the operator prerequisite of the integration itself (Integrations Console creation as a connectable account, declared scopes, redirect URL, Vercel's approval/sharing path); the connection page flow (one page, two doors; box choice in plain words, tier routing; Door 2's guided walk-through with probe-and-confirm and nothing else at setup); the install round trip — install link out, one-time code back, server-side exchange for the long-lived installation token — enrolled through the existing probe/store path with the declared box and the installation's identity (team, configuration) recorded; the Tier 2 setup section's plain-words re-presentation (labels and explanation only); declared-box display in `vercel_whoami`; disconnect (in-product revocation) across account kinds; **the two-layer box model: per-team ceilings accumulated across installs, the per-connection working-box setting, the agent-called flip tool (catalog-reachable at minimum; front-door only inside the measured OP-1 budget), the plain-language ceiling/flip reporting in the connection's self-description, and the widest-ceiling copy on the grant surfaces**; **the posture self-report as information (credential width, capabilities available, box state, the user's own pre-existing settings — IN-17; no switchboard is built)**; tests with fakes modeled on the verdict's **documented real shapes** for the install code exchange and installation reads; register/STATUS/DECISIONS updates in the implementation PR.

**Out:** building on Sign in with Vercel's API permissions while they remain private beta (the design is shaped so that tier can be swapped in at GA without changing the box model — the swap is a future card, not this one); per-permission user dials (the beta catalogue — roadmapped, not built); any change to IN-04's rules, the purchase policy, production rules, or existing accounts'/connections' behavior; **any front-door change beyond the flip tool's conditional promotion above, and any other new MCP tool**; migrating the owner's own god-mode enrollment (his Tier 2 posture is decided and proceeds independently of this build).

## Acceptance (live probes — merged code never closes the finding)

- **A-1 (team box, install flow):** a fresh end-user-shaped connect starting at the connection page's **Door 1**: no pre-enrolled token; the user installs the integration on **a team** from Vercel's own pages (pure clicks — the user never handles a token value), completes the standard connection; `vercel_whoami` shows the declared box (team), the standard profile, and the agent performs standard-tier work on that team inside the integration's declared scopes.
- **A-2 (project box):** the same flow with the working box stamped at **one project**: a read outside it is refused by our per-call enforcement and says so plainly; where the install granted selected projects only, the install's set corroborates the pin.
- **A-3 (whole-account box):** the flow routes to the token tier with the reason stated; after enrollment with the explicit choice, the account reads back its declared box (whole account) and its expiry posture.
- **A-4 (the credential follows the grant, not the setting):** choosing a different box *at sign-in*, or widening beyond the ceiling through a new grant, re-issues/re-enrolls the credential to match, and the prior credential's state is verified dead or honestly reported. **In-ceiling working-box flips (A-8) are settings changes only — the credential behind the connection is preserved untouched** (no rotation, no re-enrollment), and the probe verifies the same credential identity before and after each flip.
- **A-5 (revocation, all directions):** in-product disconnect → the stored credential is gone on read-back and later calls fail honestly; Vercel-side uninstall → the next call fails honestly and the posture shows the credential dead; installer-loses-team-access (platform disable) → the next call fails honestly and the posture names the cause class instead of a generic failure.
- **A-6 (no regression):** existing token enrollments (team/project), DCR clients, the Muse client-metadata path (AUD-G), and every other client connect and behave as before; `npm run check` and the full suite green at the implementation head; the front-door listing/token budget unchanged.
- **A-7 (fixture discipline):** live probes run against scratch-class accounts/projects created for the probe and torn down with deletion verified (rtc-scratch discipline). The owner's real accounts and connections are never probe fixtures — **A-13 is the single named exception**: an owner-directed probe on the owner's own god-mode connection, gated on his word at run time.
- **A-8 (flips inside the ceiling are instant):** on a connection whose granted ceiling is a team, the agent flips the working box team → one project → team on the user's word, with no re-login and no new grant; each state reads back correctly in the self-description, each flip is journaled, and a read outside the narrowed project box while it is set is refused plainly.
- **A-9 (beyond the ceiling is honest, then walkable):** the agent attempts to widen beyond the granted ceiling — to an ungranted project in an installed team, and separately to a team never installed: each answer names, in plain words, the specific one-time step that applies (Manage Access on Vercel's dashboard; a fresh install) — no silent failure, no pretended flip, no generic error. After the user completes that step, the same flip succeeds without re-login of the existing connection.
- **A-10 (the agent can say it unprompted):** a freshly connected agent, given only the connection's self-description output, can state in plain language: the current working box, the granted ceiling per installed team, which flips are instant and which need which one-time step. The probe is run cold — the relay text is judged from the output alone, not from documentation — and it fails if the relay describes accumulated installs as "account-wide" in any wording.
- **A-11 (a second team onboards as clicks, not tokens):** with Team A installed and in use, the user wants Team B reachable: the agent offers the install, the user completes it on Vercel's pages, and the connection then reports both ceilings with independent working boxes per team — no token handled by the user at any point, and Team A's box, flips and journal are untouched by Team B's arrival.
- **A-12 (an account-level ask from a team seat is answered honestly):** on a Tier 1 connection, the user asks for an account-layer action (create a team): the answer states plainly that this seat cannot reach the account layer and offers the token tier as the route to that power. No team is created, no install bundle is silently substituted, and the journal shows no attempted write.
- **A-13 (account-layer reference probe — owner-gated):** gated on the owner's god-mode enrollment having landed AND his word at run time: through his own full-account connection, create a scratch team (empty — no members, no projects), read back that it exists, delete it, and read back that it is gone. This proves the account layer end-to-end on the reference implementation: the one box no install can imitate, exercised and then removed, minutes-lived.
- **A-14 (Door 2 walk-through, end to end):** a fresh end-user-shaped connect at the connection page's **Door 2**, following only the page's own steps: the tokens button opens Vercel's plain Account Tokens page (the documented URL, no prefill of any kind); the user creates a Full Account token with an expiration of their choosing, pastes it once; the server probes it and **reads back "Account-wide" for the user's confirmation before the seat activates**; the activated seat then works at the account layer, restrained by the connection's chosen profile. A narrower token pasted at the same door reads back its true scope and activates as that box, labeled as such. **Setup at this door contains nothing else** — no permission UI, no profile pick: steps, paste, probe, confirm.
- **A-15 (posture self-report — information, not restraint; replaces the withdrawn switchboard probe):** on a connected seat, the self-description states in plain words the credential width it holds, the capabilities available to it, its box state, and the state of the user's own pre-existing settings (e.g. the production switch — ON by default in god mode, flippable by the agent on the user's word per IN-09). A cold agent reading only the report can state the connection's posture unprompted. Nothing in the report gates an action, and **no built switchboard exists to flip** (IN-17): IN-18's legible-refusal behavior is judged under A-9/A-12's honesty probes and the product's general refusal surfaces, not here.

## Build notes

- Additive or it doesn't ship: like AUD-G, every existing path must keep working byte-for-byte for existing accounts and clients; the new surface is a new door into the same account machinery, not a replacement of it.
- The account store already keys `team` and `team/project` and already records probe + scope; the declared box is an additive field in that same shape, with the same journaling discipline as every other account change.
- Fake-first development is how this fleet keeps shipping fixture blindness (PR #223, VMCP-022, VMCP-023): every new fake for this build cites the documented shape it models — for this card, the research verdict's shapes (the install exchange response carrying a single `team_id` and a configuration id; the long-lived installation token; the disabled-on-installer-departure behavior) — in the test or its fixture file.
