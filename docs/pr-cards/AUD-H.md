# AUD-H — Deployment execution segment: real provider target encoding, legible failures (VMCP-023 delta)

Status: IMPLEMENTED 2026-10-28 (branch `ai/vivienne/vmcp-023-deploy-fix`, base main `898918c`) — VMCP-023 stays **open** until its acceptance probe passes live (the X-2 seed → deploy sequence completing on a fixture-class connection, after release).

**Why this card exists:** VMCP-023 (P1 · D8/D10, filed at S7) recorded that file-upload / deployment-create execution fails deterministically in the provider segment on both token scopes — `outcome_unknown` twice for `vercel_deploy_create_from_files`, once inside `vercel_dev_seed` after its project was created — while project creation and environment writes succeeded through the same machinery, and the outcome named no failing leg. The owner directed this delta packet 2026-10-28.

## Diagnosis (2026-10-28, from source + the vendored OpenAPI snapshot + S7 evidence)

Three defects, two proven from the repository's own materials, one bounded:

- **D-A (proven — response-shape recognition).** The vendored snapshot's deployment object encodes the target as nullable: `"production"`, `"staging"`, or `null`, and documents that **`null` indicates a preview deployment**. The create/verify paths of `vercel_deploy_create_from_files`, `vercel_deploy_create_from_files`' sibling `vercel_deploy_create_from_git`, and `vercel_dev_seed` / `vercel_dev_cleanup` (dev-runs) instead require the literal string `'preview'`, so a provider response in its real shape makes their `shapeResult` / verify checks throw or fail — inside `apply`, where the write executor converts the throw into a generic `outcome_unknown`. Sibling tools that already accept the real encoding (`deployment-cancel`, the deployment list projection: `target===null || target==='preview'`) prove the intended semantics inside this same codebase. The unit fakes model the deployment object with `target:'preview'` — a shape the real provider never returns for a preview — which is how this shipped green (the fixture-blindness pattern, third instance).
- **D-B (proven — illegibility, the finding's D10 half).** `src/core/write.js` converts *every* error thrown inside `apply` into `outcome_unknown` with one fixed reason, discarding the thrown error's safe provider code; `uploadFile` additionally swallows its fetch error in a bare `catch {}`, discarding even the failure class (timeout vs network vs HTTP status). No caller can tell upload from create from verify. The S7 cleanup evidence (a project delete recorded *uncertain* under an `applied` envelope) travelled through the same illegible path.
- **D-C (proven — the seed's upload guard mismatch, found by this card's own legibility fix).** `writeProvider`'s upload wrapper authorizes two tools (`vercel_deploy_create_from_files`, `vercel_dev_seed`) and passes the tool name through, but `client.uploadFile`'s guard accepts only `vercel_deploy_create_from_files` — so **every `vercel_dev_seed` upload threw `write_guard_unavailable` before any network call**, deterministically, on any scope. That is exactly S7's seed signature (project created and tracked, then failure in the upload segment, no deployment ever recorded), invisible until the D-B fix surfaced the code in a local reproduction of the seed flow.
- **D-D (bounded suspect — the from-files upload leg).** S7's from-files attempts also recorded **zero deployments**, so their create POST's success was never recorded either: the failure happened at or before create dispatch. The file tool passes the guard above, so its suspect leg is the upload fetch itself: it carried a bespoke **3.5 s** abort where the rest of the transport uses a 25 s bound, with no documented rationale, and a ≤2 MiB upload from a serverless function does not fit a 3.5 s budget reliably. Offline evidence cannot discriminate timeout vs an HTTP-level refusal in that leg — that is precisely what D-B's fix changes: after this card, any residual failure names its leg and safe failure class in the outcome, and the live closure probe discriminates definitively.

## Scope

**In:** a shared deployment-target matcher (`src/vercel/deployment-target.js`) applied at every `deployments_create` shape/verify check and every deployment-target inspection inside the two finding-named tools (`deployment-file-create.js`, `deployment-git-create.js`, `dev-runs.js` seed + cleanup inspectors); the upload guard's tool allowlist aligned with the provider wrapper's authorized set (both guarded deploy tools); safe failure legibility — the write executor's `outcome_unknown` gains a `failure` object carrying the thrown error's pattern-validated `code` and `leg` (operation id), never a message or provider body; `client.request` tags write-path errors with their operation leg and gives shape-check throws the code `response_shape_unverified`; `uploadFile` classifies its failures (`timeout` / `network` / `http_status` + status number) under leg `deployments_file_upload`; the upload abort aligned to the transport-standard 25 s; unit tests modeling the **real** provider shapes (preview deployment objects with `target: null`, the documented upload success body) plus legibility regressions; the register amendment, DECISIONS entry and STATUS entry recording this diagnosis.

**Out (non-goals):** sibling tools with the same literal-`'preview'` assumption outside the finding's segment (`deployment-delete`, `dev-preview-*`, `dev-integration`, `dev-observe-common`) — recorded in the register amendment as the same defect class for a follow-on packet, not silently expanded into this one; any change to replay/claim semantics, confirmation, purchase policy or production rules; any new tool; the live closure probe itself (post-release, per the pipeline rule — merged code never closes a finding).

## Build notes

- The matcher: expected `preview` ⇔ actual is `null`, `undefined` or `'preview'`; expected `production` ⇔ actual is `'production'`. Anything else does not match. One helper, used by all three tools, so the encoding is stated once.
- Legibility is additive and bounded: `failure` appears only on `outcome_unknown` results from the executor's apply-catch, and only with fields that pass strict patterns (`code`: the provider's already pattern-validated error code, an internal code, or `response_shape_unverified`; `leg`: an operation id from the server's own table or `deployments_file_upload`). Error messages and provider bodies are never copied — the existing no-secrets posture is unchanged.
- `uploadFile` keeps its single attempt (no blind POST retry) and its replay claim semantics; only the abort bound and the error classification change.
- The executor's other `outcome_unknown` sites (approval/delivery verification) are untouched: they already carry specific reasons and are not provider-segment failures.
