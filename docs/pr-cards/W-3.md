# W-3 — Ship to production + emergency rollback (Batch W, third card)

Design: `docs/designs/BATCH-W.md` §3 row W4, §4 row W-3.
Dossier: `batch-w-dossier-2026-10-30.md` §1 (W-3 rows).
Precedent: Batch P verdicts C-1..C-9; W-2's write composition.

## Scope

Two guarded writes in `src/tools/workflow-release.js`, both PR class,
profiles everyday+full, each a single step dispatching the owning
release tool through its own pipeline (`vercel_deploy_promote` /
`vercel_deploy_rollback` — their full-profile gate, expectedCurrent
proof and served-history rules apply there, never re-implemented):

- `vercel_workflow_ship_to_production` — description `{project,
  deployment, paths?, outsideApp?, reason?}`. Gates, all proven in
  `before()` before any step is planned (design W4): the candidate is
  READY; every reported check run concluded success (a project with
  no reported checks proceeds, and the receipt says `total: 0` — it
  never claims checks passed); a smoke fetch of the candidate's own
  URL (from the deployment read-back, never a caller-supplied host)
  over the given paths (default `/`) returns 2xx/3xx for every path.
  Any gate failure refuses, naming the gate. The step records the
  previous live deployment (`expectedCurrent`, read from the alias
  list, which must be complete and consistent) and the workflow's
  inverse is the rollback to it.
- `vercel_workflow_emergency_rollback` — description `{project,
  deployment?, outsideApp?, reason?}`. With no deployment given, the
  target is the last good deployment: production deployments newest
  first, excluding the current one, each proposed to the rollback
  tool's own dry-run until one proves eligible (the tool refuses
  never-served targets inside its pipeline; at most 3 proposals). The
  covering profile's `rollback_caution` is shown in the preview.
  After the step applies, the workflow verifies by alias read-back
  and reports honestly whether errors are still occurring (error
  summary rows whose lastSeen is after the rollback moment), with
  `null` when the summary cannot be read.

## Verdicts recorded on this card

- **W3-C1 (smoke host):** the smoke fetch targets only the candidate
  deployment's own URL from provider read-back; caller input supplies
  paths only (validated: leading `/`, no `..`, no query/fragment).
  Redirects are not followed; 2xx and 3xx both pass (the design's
  rule). No body is read or returned — status only.
- **W3-C2 (zero checks):** the W4 gate is "all reported checks
  concluded success"; zero reported checks is disclosed in the
  receipt, not dressed as a pass and not a block.
- **W3-C3 (target search):** eligibility of a rollback target is
  proven by the rollback tool's own dry-run, not by any workflow-side
  served-history model (the read tools do not expose servedAt).
- **W3-C4 (checks gate, literal):** W4's words are "all its checks
  concluded success", so the gate is literal — a check that concluded
  `skipped` or `neutral` refuses the ship, named in the refusal. The
  owner who judges it fine still has `vercel_deploy_promote` directly
  (the area tool carries no checks gate); the workflow's gate is a
  stated convenience, not a platform rule (IN-18).
