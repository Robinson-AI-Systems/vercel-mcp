# F-1 — Deployment protection and bypass

Status: in progress · Parent: BATCH F (`docs/designs/BATCH-F.md` §§1–4) ·
Dossier: `batch-f-dossier-2026-10-30.md` in the audit goal workspace
(full endpoint contracts, shape map, and the design-vs-contract
dispositions this card follows).

## Purpose

Deployment protection decides who can view a project's deployment URLs,
and Batch F's first card builds its control surface: read the current
protection state, change Vercel Authentication, password protection and
trusted IPs as guarded writes, and manage automation-bypass secrets and
shareable links without a secret ever passing through chat (design F3).

## What ships

1. **Operations** (`src/vercel/operations.js`): one addition,
   `aliases_protection_bypass_update` (PATCH /aliases/{id}/protection-bypass),
   verified against the pinned snapshot. The project protection fields ride
   the existing `projects_get` / `projects_update` (PATCH /v9/projects/{idOrName})
   and `project_protection_bypass_update` operations.
2. **Reads** (`src/tools/protection.js`): `vercel_protection_get` (the four
   protection fields projected from the project record — password protection
   reports presence plus its scope only when the record carries it as a
   string, because the pinned snapshot documents that field as an opaque
   object; dossier §4.2) and `vercel_protection_list_bypass` (notes, dates,
   env-var flag and scope only). The bypass map on the project record is
   keyed by the secret itself; keys are used inside the handler only and
   never appear in any result, preview or audit record (entries are
   identified by a SHA-256 fingerprint wherever state must be carried).
3. **Guarded writes** (same module), all production-class (design F1:
   protection changes decide who can view live deployment URLs):
   - `vercel_protection_set_vercel_auth` — PATCH `ssoProtection`
     ({deploymentType} or null). Loosening (turning off, or moving to a
     narrower scope by the rank all > prod-URLs-and-previews =
     all-except-custom-domains > preview) is declared through `access()`.
   - `vercel_protection_set_password` — PATCH `passwordProtection`;
     `secretIn` — the password is consumed from a setup-page pending input
     (kind `deploy_password`) inside apply, never an argument; turning on
     from off requires one. Loosening declared through `access()`.
   - `vercel_protection_set_trusted_ips` — PATCH `trustedIps` (IPv4/CIDR
     only; the contract does not support IPv6). Catalog marks the tool `A`:
     enabling widens access and says so; disabling narrows.
   Each settings write re-reads the project inside `requirePreDispatch`
   and refuses if the field drifted since the confirmed preview, and
   verifies by independent read-back.
4. **Bypass secrets**: `vercel_protection_create_bypass` sends a bare
   `generate` body — the pinned snapshot makes `generate.secret` optional
   and constrains a supplied value to exactly 32 alphanumeric characters
   ("don't send it for oauth2 tokens"), so the provider mints the secret;
   the tool proves exactly one new key exists in the returned map by
   diffing against the preview's fingerprints, and delivers it through
   the one-time secret page (kind `protection_bypass`) — `secretOut` +
   one-time delivery, access-widening declared. (Build correction to the
   dossier's house-pattern assumption, 2026-10-30: client-supplied values
   are pattern-bound, provider minting is the contract-true route.) `vercel_protection_revoke_bypass`
   addresses an entry by its note (plus optional createdAt when notes
   repeat), re-reads and fingerprint-matches it at apply, and revokes
   with `regenerate: false` (the catalog's revoke is a plain revoke; no
   new secret is minted). Revoking the entry that serves as
   `VERCEL_AUTOMATION_BYPASS_SECRET` warns in the preview that builds
   using it stop bypassing until redeployed (design F3). Integration-owned
   bypass entries are listed as integration-managed and cannot be revoked
   here.
5. **`vercel_alias_set_shareable_link`** — create or revoke a shareable
   link for one alias/deployment URL. Create PATCHes the alias
   protection-bypass (optional `ttlSeconds`); because the pinned snapshot
   documents that response as opaque, the minted secret is recovered from
   the documented alias read (`release_alias_get`) by diffing the
   shareable-link entries before/after — if no new entry appears the
   write reports an unknown outcome rather than inventing a link
   (dossier §4.3). The secret goes to the one-time page (kind
   `shareable_link`); revoke identifies the entry by createdAt and
   revokes by its internally held key. Access-widening declared;
   one-time delivery only when creating.
6. **Catalog and pins**: the eight F-1 rows in TOOL-CATALOG gain their
   built marks with this PR; registry order pins in
   `tests/unit/registry.test.js` and the front-door count in
   `tests/unit/front-door.test.js` move by eight. STATUS bullet in this
   PR. No database change.

## Self-review checklist

- [ ] Write-contract behavior for all six writes through the shared
      machinery: dry-run dispatches nothing, no-confirm dispatches
      nothing, preview-mode connection refused for production changes,
      read-only profile refused, protected target refused before apply.
- [ ] No secret in any surface: bypass keys and the deployment password
      are asserted absent from results, previews and audit entries in
      tests; the password exists only as a consumed pending input.
- [ ] Exact dispatched bodies asserted against the contract shapes
      (ssoProtection/passwordProtection/trustedIps PATCH fields, bypass
      generate/revoke bodies, alias ttl/revoke bodies), each pre-validated
      with `validateRequest` against the pinned snapshot.
- [ ] Loosening cases declare access widening (auth off, password off,
      scope narrowing, trusted-IP enable, bypass create, link create);
      tightening cases do not.
- [ ] No live exercise: fakes only. Live acceptance rides the nightly
      promotion and the audit's closure probes.
