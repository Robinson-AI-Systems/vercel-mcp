## What this card builds

- `vercel_integration_list` (read) — GET
  /v1/integrations/configurations with the contract's required
  `view=account`. Rows are shaped defensively across the snapshot's
  two list variants (with/without the embedded integration object);
  rows without a usable id are counted as `skipped`, never silently
  dropped.
- `vercel_integration_get` (read) — the configuration plus GET
  /v1/installations/{id}/resources. Resources are shaped to
  internalId (the identity the connections endpoint takes, dossier
  S-5), name, product, status and billingPlanId; resource metadata
  and protocolSettings are never returned (they can carry partner
  configuration). Billing plans surface from the resources'
  billingPlanIds and the configuration's transfer-request billing
  plan when present — the result states which sources answered.
- `vercel_integration_remove` (D Cp) — DELETE the configuration,
  verified by a 404 read-back. The preview lists the connected
  projects and the resources that go with the installation. The
  configuration record does not carry the injected variable names
  (they live on linked stores' project metadata), so the preview
  says exactly that instead of inventing a variable list.
  Production-class when the installation is connected to at least
  one project (it may inject production variables — the Cp rule),
  with the reason stated.
- `vercel_integration_connect_resource` (Cp) — POST the connection
  for a resolved project. Production-class when the caller's
  environment selection includes production, or when it is omitted
  (the provider default may include it); a preview/development-only
  selection is not. Verify reads the configuration back and checks
  the project is now listed; where the record doesn't say,
  confirmed stays null.
- `vercel_integration_create_store` ($) — POST
  /v1/storage/stores/integration/direct. Before() reads the
  product's plans from the pinned plans endpoint; the preview lists
  them with the provider's own price strings (the contract prices
  plans in strings, dossier S-6 — no cents figure is synthesized).
  A named plan is used when `billingPlanId` is given, otherwise the
  provider default applies and the preview says so. Prepayment
  plans take the caller's explicit `prepaymentAmountCents` (the
  contract's own field, ≥50) as the quantified declaration; other
  plans declare metered/recurring spend. The create response's
  `secrets` block is dropped in the shaper — it never reaches the
  result, journal or replay (planted-secret scans pin this).
- `vercel_storage_get_store` (read) — GET /storage/stores/{id}
  (unscoped in the contract). The snapshot's store schema documents
  no id/name/type/size/region (dossier S-2): the tool returns the
  documented fields always (status, usageQuotaExceeded, connected
  projects from projectsMetadata with environment NAMES only) and
  identity/size/region when the provider includes them, null when
  absent.
- `vercel_storage_create_blob_store` ($) — POST /storage/stores/blob
  with the contract's region enum; metered spend (storage and
  operations beyond included usage), pricing link in the preview.
- `vercel_storage_delete_blob_store` (D) — DELETE
  /storage/stores/blob/{id}, verified by read-back. The preview
  always carries the design's sentence: "every file in the store
  is deleted; this cannot be undone". While Batch P's app profiles
  do not exist, the profiled-store refusal is structural: a store
  connected to any project requires `outsideApp: true` — the
  caller must name the act as store-level, not one app's view
  (dossier §4 M-3 note).
