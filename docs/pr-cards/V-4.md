## Implementation contract and seam checklist

- V-4 five sandbox tools and V-5 one signed synthetic webhook sender use V-1 run and object ownership and shared guarded write helpers. No additional external provider is introduced.
- Bind to the pinned vendor Vercel OpenAPI for every provider method, validated body/query/response; do not guess a v4 API endpoint from a separately deployed SDK. In-memory unsigned/incomplete provider claims are not acceptance.
- Preserve exact account, preview connection, nonproduction purpose, run and sandbox identity; keep independent before/after checks and durable intent prior to ambiguous provider writes.
- Provider-side metered capabilities require truthful pricing/risk disclosure, user-specific delegated authority and actual policy under the Oct 16 owner decision. The implementing agent has no autonomous spending permission, no live access or authorized charged fixtures.
- Use disposable Postgres for two concurrent sandbox reservations, stateful provider fakes for status/command/read/write/stop, and bounded/SSRF/signed-webhook tests. Exercise the registered tools through all existing doors, followed by full repository CI.
- Every tracked session must have exact native cleanup. Secret publication is permitted only through the authenticated one-time setup-page mechanism; never return signed secret, sensitive body or token-shaped URLs.

### OpenAPI drift check B — discovered exact-head mismatch

Vercel's pinned 2026-10-11 /v4/sandboxes schema contains ambiguous `snapshotExpiration.oneOf: [{}, {type:integer}]` which rejects every integer, so do not send that optional field for nonpersistent sandboxes. The snapshot also mistakenly marks query `cmdId` required for POST /v2/sandboxes/sessions/{sessionId}/cmd, although provider public SDK `runSessionCommand` takes sessionId and body only and cmdId is returned, not supplied. `src/vercel/openapi-validation.js` has an exact operation+param exception for ONLY this impossible request parameter; all other required fields and native body schema remain validated. CI new regression validates real pinned create/command/read/stop methods. No provider call made.

### Native return-envelope correction — 2026-10-16

The exact pinned POST /v4/sandboxes returns `{sandbox,session,routes}`; GET session returns `{session,routes}`; command POST/GET returns `{command}`. The implementation must check session.id/projectId/sourceSandboxName and command.id/sessionId inside those envelopes; treating top-level id/sessionId as native was incorrect and is fixed. Provider fixtures and CI are separate from actual live service acceptance.

## Native command output result-handling — follow-up implementation

The run action starts a bounded command; action=inspect and commandId reads its exact native command status and bounded (12 KB / 64-record) ND-JSON stdout/stderr log stream with no raw credentials or transport body in audit. The first three log lines are previewed and safe text is stored for 10 minutes in the pre-existing bearer-bound vercel_get_result store. If the command is still running or streaming fails, the receipt marks output incomplete/unavailable rather than incorrectly claiming empty output. Original tool count remains five.

## Merge-blocking self-review finding: native result IDs

Generic defineWrite intentionally did not emit providerResult/verification payloads, so initial multi-step sandbox create/run omitted the session and command ID necessary for follow-up tools. This is now corrected via a generic optional provider-neutral `publicReceipt` hook that exposes only each tool's explicitly curated, verified fields (session/command identity, bounded redacted result handle, file count or stop status). All other guarded writes retain the exact prior behavior. This integration correction is tested without weakening central write/security guards.
