## What this card builds

1. **`vercel_profile_draft`** (read, all profiles, listings front_door +
   compact) — turns caller-supplied codebase findings into a draft
   profile (validated by the app-guard `validateProfile`) plus the
   `APP-NEEDS-<APP>.md` text. It never fetches code itself and never
   writes anything. Findings use a CLOSED vocabulary; unknown keys —
   top-level or nested — are reported in `unmapped`, never guessed into
   the profile.
2. **`vercel_workflow_project_setup`** (guarded write, full profile,
   safety P — C for production parts) — sets up Vercel for a NEW project
   from a short description: project (optionally Git-linked), framework
   and build commands, custom environments, variable names (generated
   values dispatched; value-less names returned as pending-input
   requests), project domains, protection. Idempotent: before() reads
   live state through the registry and plans only what is missing, so a
   second run creates nothing. Ends by writing a draft profile row
   (`known_apps`, status `draft`, source `draft`, account-scoped) and
   returning the APP-NEEDS text — returned, never committed elsewhere.

## Composition verdicts (this card's additions to the dossier)

- **C-1 — Write workflows compose through the registry.** The registry
  enforces `isGuardedWrite` for every `writes: true` tool, so the setup
  workflow is itself a `defineWrite`; its context passes `dispatchTool`
  through, and every step executes ONLY by dispatching the owning area
  tool (BATCH-W decision W1 applied here): step dry-runs are dispatched
  inside `before()` to build the one combined preview (W3), and on
  confirm the steps dispatch in order with `confirm: true` and
  requestKeys derived `<workflowKey>-s<n>`, stopping at the first
  failure. No step is a private provider path; each step's own guards,
  classifications and purchase policy apply inside its own pipeline.
- **C-2 — Value-less variable names are never dispatched.** Tools
  consume pending inputs; they never create them (the readiness
  pattern). A name with no `generate` is reported in the workflow result
  as a pending-input request with the exact follow-up call. A dispatched
  step that refuses stops the workflow and its named reason (AUD-AH)
  is reported verbatim with the steps already done.
- **C-3 — Node version is guided, never set** (dossier R-2: no tool
  changes a project's Node version). The description's `nodeVersion`
  appears in the preview and result as a guided step, and in the draft
  profile + APP-NEEDS text.
- **C-4 — Spend lives in the step, not the workflow (amended at build).**
  The catalog row carries no `$` and check-writes enforces that: the
  workflow declares no spend of its own, because it never touches the
  provider. The metered step (`vercel_project_create` on a Git import)
  declares its spend and runs its own purchase policy inside its
  dispatched pipeline — which is also why the workflow's confirm can
  never bypass a step's gate: on a delegated connection a gated step
  stops the workflow with its own refusal (C-2).
- **C-5 — Production is classified whole-workflow.** `production()` is
  true when the description carries production env targets, domains or
  production protection, so preflight's mode guard refuses the whole
  setup on a preview connection (design P-3 test) instead of applying
  the non-production half. Steps re-classify themselves as usual.
- **C-6 — The draft row is the workflow's own local write**
  (`db.upsertKnownApp`, account-scoped), not a dispatched step; the
  workflow's inverse points at each applied step's own change-log row
  for undo plus removal of the draft row on the setup page.
- **C-7 — Draft mapping.** `domains` → `owned_domains`; `envNames` →
  `expected_env.production` (per-target split is setup-page work; the
  doc text says so); `crons` → `expected_crons`; package.json script
  NAMES appear in the APP-NEEDS text only (no profile field holds
  them); a draft profile's `vercel_account` stays unset (IDs/slugs are
  setup-page data, dossier S-6).
- **C-8 — A stopped workflow reports through the journal.** The write
  machinery returns a public receipt only for a fully confirmed write,
  so a workflow that stops mid-flight ends `applied` with
  `confirmed: false`, and its own change-log row carries the partial
  report (steps done, the step it stopped at with its named reason,
  and per-step undo pointers in the inverse). Each applied step is
  independently journaled by its own tool, so `vercel_recent_changes`
  is the complete record — the journal-everywhere doctrine, not a
  fabricated receipt.
- **C-9 — A workflow's advertised schema stays compact (build
  catch).** Compound workflow tools join the front door by rule, under
  OP-1's hard 5,000-token cap; a 25-field inline schema for the setup
  description measured 893 tokens for one listing entry and broke the
  cap. The tool therefore takes ONE `description` object argument —
  the readiness tool's inline-spec precedent — with the field contract
  enforced by hand in the validator and written out on this card and
  in the module. Descriptions also stay within the 160-character
  listing bound. Membership follows the same budget discipline:
  `vercel_profile_draft` ships catalog-only (like the other profile
  reads) rather than spending front-door tokens on a niche authoring
  tool.
