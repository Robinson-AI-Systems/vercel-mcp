## U-1c (PR #152): safe continuation of audited flag pages

Pinned Vercel SDK listFlagsV2/listFlags response models declare `data` and
`pagination.next`. A prior projection stripped the cursor, preventing a
consumer from requesting a later page. The audited universal read now projects
only a bounded opaque next cursor (or an explicit null), never the raw
pagination object; it rejects malformed, control-bearing and credential-shaped
cursor values. A missing provider cursor remains unverified completeness.
Caller-provided cursor passes the existing full pinned query validation,
scope/project proof, team binding and 64-KiB transport cap for every page.
No other API family or write is enabled. Fake HTTP tests cover next-page
query propagation, omitted/hostile pagination, metadata-only output and
cross-project denial. Connected real-provider acceptance is still pending.

## U-1d (PR #153): scope-verified team flag inventory

A team/full stored connection may request the pinned `listTeamFlagsV2` GET
with the required team path bound exclusively from the encrypted account, no caller project/team override, and at most five rows. Before returning
any provider row, the handler requires its exact project ID, checks any
declared team ID, and independently re-reads each distinct project to verify
the same encrypted selected team. Missing/foreign/malformed identities, pages
larger than five, absent required pagination and project-only accounts fail
closed. Results contain metadata fields and a bounded opaque cursor only,
never variants, rules, environments or identities. At most five extra provider
GETs per invocation; each page is reverified. Fake provider tests exercise
same-team project proofs, scope denials, oversized pages and private-field
omission. No deployment/provider proof and no writes.

## U-1e (PR #154): deployment flag status without flag values

A project-key connection can read the pinned `getDeploymentFeatureFlags`
endpoint only for a deployment proven by independent GET to belong to its
stored exact project. Caller cannot select a team, another project or a
deployment URL. Check both deployment/provider status identities and deny
missing/mismatched identities. Return strictly bounded observed/reported
flag counts; never flags, variants, conditions, environments or raw status.
Deny unknown or oversized status payloads. Fake HTTP tests cover real
pinned request shapes, scope, cross-project/response contradictions and
secret-bearing input omission. CI proves code only, not genuine provider,
D-2 or hosted Hub acceptance; no writes or new RTC authority.

## U-1f (PR #155): provider-reported flag capacity overview

The already-audited `getFlagSettings` GET previously discarded useful
documented `metadata`. After the existing exact project/team identity GET,
it now returns the provider-reported active/archived flag counts, segment count,
pack byte size and Boolean enabled state. Counters must be nonnegative safe
integers; malformed, foreign or incomplete provider metadata is refused.
No raw flag entities, environment values, token material, targeting details or
rule data pass the projection. Fake HTTP tests cover valid/foreign/malformed
metrics, complete request validation, secret-field omission and project-only
scope. This is not real provider/cost/Hub acceptance.

## U-1g (PR #156): exact flag revision history

Improve `listFlagVersions` from a generic shallow projection to a
bounded 20-item version-history diagnostic. After the already-established
project identity GET, independently GET the exact flag ID and require the
provider's flag ID and project to match before retrieving version details.
Return only safe version IDs, integer revisions, timestamps and bounded
provider cursors; deny wrong flag IDs, duplicate/malformed entries,
oversized/malformed pages and scope overrides. Author names, messages,
variant values, rules and environment state never enter output. No caller
flag-slug ambiguity, production mutation, new secrets or write grant.
SDK/pinned schema mapping and fake HTTP tests prove code only; genuine
provider shapes and D-2/Hub connected acceptance remain outstanding.

## U-1h (candidate PR #159): exact ownership proof for universal project reads

An explicitly team-scoped connection may address multiple provider projects,
so successful GET by project ID is **not** sufficient identity evidence. The
existing selected-account read now requires returned project ID **and**
affirmative `accountId === stored team_id` before it executes any
universal feature-flag GET. Missing ownership and contradictory or foreign
team ownership fail closed (including project-only connections).
`tests/unit/universal-read.test.js` verifies missing, foreign, correct and
project-only cases against fake GET responses. Provider production shapes and
actual authenticated owner/RTC reads remain separately unverified.
The PR also incorporates permanent actionable owner recovery, PR-number batch
alignment and corrected verified hosting/account status into current instructions,
not a new policy file. No migration, spend, token scope or deployed release.
