## What this card builds

- `vercel_logs_query` (read) — POST /v2/observability/query. Caller
  picks the metric (the live Query reference's dotted ids, e.g.
  `vercel.request.count`); optional project narrows the scope to
  `{projectId}`, otherwise the scope is the selected team
  `{ownerId}` (dossier S-1: the snapshot leaves `scope` untyped; the
  scoping model is the reference's own project-vs-team-wide model,
  and the tool echoes the scope it sent). Window defaults to one
  hour, refuses beyond seven days; at most 50 rows are returned and
  a larger provider page is reported as truncated, never hidden.
  The snapshot documents the 200 response only as an untyped object,
  so rows are extracted defensively (array body or a data/rows/
  results/events member) and shaped to scalar values only; a
  response with no row array says so instead of inventing rows.
- `vercel_logs_errors_summary` (read) — the same endpoint specialized:
  metric `vercel.function_invocation.count`, filter `errorCode:*`
  (the reference's own exists-operator example), grouped by
  errorCode for one project. Each row is shaped to the catalog's
  promised fields — message, count, first/last seen, example request
  ID — taking each from the provider row when present and reporting
  null plus a `fieldsPresent` list when the provider did not supply
  it (dossier S-9). Nothing is synthesized.
- `vercel_analytics_pageviews` (read) — GET
  /v1/query/web-analytics/visits/aggregate with the contract's own
  dimension enum (`by`, 1–2 dims), a window (default 7 days, max 30)
  sent as since/until, and the contract limit (≤100). Rows keep the
  documented dimension fields plus the numeric measure keys actually
  present, and the result names those measure keys (`measures`) —
  the contract does not statically name them (dossier S-4). Groups
  beyond the limit fold into an "Others" row per the contract; the
  result says grouping is on.
- `vercel_analytics_set_web_analytics` ($) and
  `vercel_analytics_set_speed_insights` ($) — guarded writes over
  POST /web/insights/toggle and POST /speed-insights/toggle
  (projectId query only in the contract, so the ops are declared
  unscoped like the account-layer ops). Turning ON declares metered
  spend (usage beyond included events is billed; the preview links
  https://vercel.com/pricing); turning OFF declares $0. The toggle
  changes a project's data collection, not its deployments or
  traffic, so it is not production-class (the catalog carries `$`
  only). Verify reads the applied `{value}` back from the toggle
  response shape via a project read; a provider refusal (e.g. the
  documented 402) classifies with its remedy, never pre-judged
  (IN-18).

## Transport note (dossier S-10)

The observability query is a POST that only reads, but the provider
client classified every non-GET/HEAD op as a replay-claimed write —
a read_only connection could never have run a Prof-R tool. The OPS
entry for `observability_query` is therefore declared
`readOnly: true` and the client's write classification honors that
one explicit flag; every other op is unchanged, no surfaced error
shape moves, and POST stays outside the transport's retry set, so a
failed query surfaces once instead of being silently retried.
