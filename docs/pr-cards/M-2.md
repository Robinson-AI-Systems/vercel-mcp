## What this card builds

- `vercel_drain_list` (read) — GET /v1/drains, optionally per
  project. Each drain is shaped to id, name, status, data kinds
  (the `schemas` keys), destination **host** + encoding + header
  NAMES, projects, sampling rates, first-error time and disable
  reason. The delivery secret and header values are never returned.
  The catalog promises "last delivery"; the contract carries no
  such field (dossier S-3) — status + firstErrorTimestamp are what
  the tool reports, and the description says so.
- `vercel_drain_create` ($ C) — POST /v1/drains for the documented
  **http** delivery (dossier S-8: otlp/clickhouse/s3 deliveries are
  list-visible but not creatable through v1 tools; the universal
  write tool is the escape hatch and the description says so). The
  destination must be a public HTTPS URL: non-HTTPS, loopback,
  private/link-local IP literals, `localhost` and dotless intranet
  names refuse before dispatch. Callers supply data kinds as a
  kind→version map (the contract leaves versions free strings);
  the default is logs at `v2`, the only version literal the
  contract itself carries. Header values and a delivery secret are
  NOT accepted as tool arguments in v1 — the preview says to add
  them in the dashboard or via the universal write tool. Spend is
  metered per GB with the pricing link in the preview.
- `vercel_drain_delete` (C) — DELETE /v1/drains/{id}, verified by a
  404 read-back.
- `vercel_drain_update` (P; C when widening) — PATCH with only the
  fields the caller named. The before-state is read first; the
  preview is a before/after list, and widening (resume, a new
  destination host, added data kinds, more projects, a higher
  sampling rate) is named as widening in the preview — the class
  distinction the design draws (the executor confirm-gates every
  guarded write in this generation; the preview carries the P/C
  semantics honestly).
- `vercel_drain_test` (P) — POST /v1/drains/test. A failed delivery
  test is a 200 with an `error` field in the contract, so the
  receipt reports `delivered` truthfully instead of dressing a
  failed test as a success; destination rules match create.
- `vercel_webhook_list` (read) — GET /v1/webhooks (bare array in
  the contract). URL **host**, events, projects; list objects carry
  no secret in the contract and none is shaped.
- `vercel_webhook_create` (C 1x) — POST /v1/webhooks. Event names
  validate against the pinned snapshot's own event enum (read from
  the snapshot at runtime; an unknown event refuses by name). The
  endpoint must be public HTTPS like a drain's. The response's
  signing `secret` is captured out of the shaped result, stored
  through the one-time-secret machinery, and only the reveal
  reference is returned — the secret never appears in the tool
  result, the audit journal or the replay record (planted-secret
  scans pin this). Account webhooks are Pro/Enterprise-gated by
  Vercel; a provider refusal classifies with that remedy (IN-18).
- `vercel_webhook_delete` (C) — DELETE /v1/webhooks/{id}, verified
  by a 404 read-back.

None of the M-2 writes is production-class: the catalog marks them
C/P/$, and BATCH-B defines C to include "data leaving the team" as
a non-production step; `production()` returns false with that
reason stated on each write.
