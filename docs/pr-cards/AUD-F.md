## Scope
**In:** `probeToken`/`storeToken` scope-awareness for the project path; the client/operations seams that path needs (scoped reads that do not attach `teamId`, on the existing `teamScoped: false` precedent); a setup failure surface that names the failed probe leg (a stable leg/error identifier, never the token value and never a provider response body); fake-vercel scoped-token modeling + the tests in Acceptance; the live enrollment of the rtc-scratch fixture as the closing probe (owner session).
**Out (non-goals):** team-token and full-token probe behavior (byte-for-byte behavior preserved — see regression acceptance); token creation/removal tools (O-3's own scope); the enrolled-token expiry surface (AUD-E); any change to what enrollment *authorizes* (guards downstream of the credential are untouched — a read probe still proves access, not write permission, per the file's standing comment); X-2's write run itself (it starts once enrollment lands).

## Build contract (direction — the investigation is the builder's, the acceptance is fixed)
- **Project path rests on in-scope reads.** When `projectId` is supplied, verification must be satisfiable by a token that can do nothing outside that project: derive the proof from the reads a project-scoped token can actually perform — the scoped project list (scope inferred, no `teamId` attached) and/or the direct project read (`projects_get`), whose result carries the project's owning account/team ID — and check that derived team against the requested `teamId`. `user_get` and `teams_list` must not be load-bearing for this path: refused or empty answers from them cannot fail an otherwise-proven project enrollment. The exact seam (which read is authoritative, how the team's slug/name label is obtained for the account row when `teams_list` is unavailable to the token) is the builder's design decision, recorded in the implementing PR; if the label cannot be obtained from an in-scope read, store the best verified label available rather than failing the enrollment.
- **Team/full paths are unchanged.** With no `projectId`, and for tokens whose visibility is broad, the existing probes, scope classification (`team` / `full`), the broad-visibility check and the `allowFull` owner allowance keep their current semantics and current errors.
- **Scope is still proven, not asserted.** The project path must positively prove: the token can read the requested project, and that project belongs to the requested team. A token that can read some *other* project, or no project, fails — with the project leg named. Do not weaken `assertToken` (whitespace/format rejection stays; it is also what keeps the not-fully-excluded whitespace hypothesis testable — see Acceptance step 1).
- **Failures name their leg.** Each probe leg (input validation, identity, teams, projects, project-team match, broad-visibility, storage) surfaces a distinct, stable identifier that the setup page shows in place of — or clearly within — its failure response, e.g. "Setup failed at the projects check: the token could not read the selected project." The identifier and message carry **no** token material and **no** provider response body. The catch-all may remain for truly unexpected errors, but probe-originated failures must not fall into it unnamed.
- **No new storage shape expected.** Enrollment still lands through `storeToken`'s existing `upsertVercelAccount` with `scope: 'project'` and the `teamId/projectId` account ID. If the builder finds a schema need, it is additive-only and called out in the PR — otherwise stop (below).

## Acceptance (derived from VMCP-022's failed probe — executable)
- **Scoped-model enrollment:** against the fake in scoped-token mode (user/teams refused-or-empty; projects returns exactly the one scoped project, owned by the requested team), `storeToken` with that project's ID succeeds and persists an account with `scope: 'project'`, the `teamId/projectId` account ID and the project name — the exact enrollment that failed live on 2026-10-28.
- **Negative project cases still refuse, legibly:** scoped fake returning a *different* project → refusal naming the project leg, nothing persisted; scoped fake returning no projects → refusal naming the project leg, nothing persisted; a project whose owning team differs from the requested team → refusal naming the match leg.
- **Whitespace hypothesis stays testable:** a token value containing whitespace is refused at the input leg, named as such (proving the instrument can separate the two 2026-10-28 hypotheses).
- **Regressions:** team-token enrollment and broad-token behavior (refused without `allowFull`, enrolled as `full` with it) behave exactly as at baseline; the pre-existing token-store, token-pagination, setup-page and setup-action suites pass (any intentionally changed assertion is named in the PR with its reason).
- **Failure legibility (unit level):** forcing each probe leg to fail in the fake produces a setup response (or probe result the setup renders) naming that leg — no case collapses into the unnamed catch-all message.
- **Live closure probe:** the real rtc-scratch token (or its identical re-creation, per step 1) enrolls through the hosted setup page; the receipt shows the enrolled account for the rtc-scratch fixture (the team/project account ID composed of the fixture's IDs, withheld from repo text under the secret-scan policy) with scope `project`. **Until this passes, VMCP-022 stays open** — unit-green is not closure (pipeline rule).
