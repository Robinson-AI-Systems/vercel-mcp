## What this card builds

1. **`vercel_workflow_project_health`** (read, all profiles) — one
   project's health in one answer, composed from `vercel_project_get`,
   `vercel_deploy_list` (live production + ERROR builds),
   `vercel_logs_errors_summary`, `vercel_domain_list_project_domains`,
   `vercel_cert_list`, `vercel_env_list`, `vercel_cron_list`,
   `vercel_protection_get`. Variables are judged **missing** only
   against a stored profile's `expected_env` when a profile owns the
   project; otherwise the section reports the per-target inventory.
   The project result carries the profile `app` mark when owned.
2. **`vercel_workflow_release_status`** (read, all profiles) — what is
   live (newest READY production deployment + its commit), what is
   waiting (newer builds of the production branch not yet live; READY
   previews), and the active rolling release (`vercel_rolling_get`).
   The branch anchor is the project's tracked production branch,
   falling back to the live deployment's own branch (design §W-1 note).
3. **`vercel_workflow_find`** (read, all profiles) — one search box.
   Classifies the input (URL, `dpl_` id, `prj_` id or project name,
   domain, 7–40 hex commit, branch, env key) and resolves it through
   the matching area reads; project-scoped probes walk
   `vercel_project_list` pages under the 45-second budget and stop at
   the first match. A search cut short by the budget says so and names
   the exact follow-up call; an identifier a project is needed for
   returns what it is plus the exact resolving call.
