## Diagnosis

**D-A — verify() read-backs demand fields two of three documented `deployments_get` shapes do not carry.** `GET /v13/deployments/{idOrUrl}` is a `oneOf` of three: the in-progress shape (10 props — no `projectId`, no `meta`, no `url`), the full shape (94 props), and a reduced shape (59 props — no `projectId`; `meta`/`target`/`url` present). The seed's verify demands `projectId` equality AND `meta.rtc_run` AND a preview target; the from-files and from-git verifies demand `projectId` equality. A read-back answered in the in-progress shape (the normal case seconds after a create) or the reduced shape therefore reports `confirmed: false` for a deployment that is exactly right. The fakes model the full shape only.

**D-B — the seed's first deployment is promoted, and its verify demands preview.** Live-captured record (2026-10-28 re-probe): the seed's deployment came back `READY` with target **production** — the provider promotes a project's first deployment. Against a demanded preview target, the seed could never confirm its own fixture even with perfect shapes. (The user-facing create tools keep their target demand: a user who asked for preview and got production should see `confirmed: false` and the read-back, not a silent pass. The seed is a fixture tool whose contract is a working scratch deployment on a project the run itself created and will delete whole.)

**D-C — the env inventory demands a pagination object the documented env-list contract does not guarantee.** `GET /v10/projects/{idOrName}/env` is a `oneOf` of three: a single-env object (by-id; never queried here), `{envs, pagination}`, and **`{envs, hiddenProductionEnvCount}` — no pagination**. The deletion inspect runs the reply through `countComplete`, which throws without `pagination`, so a branch-2 answer blocks cleanup and `vercel_project_delete` for a project whose inventory is in fact fully visible. That branch is also meaningful: `hiddenProductionEnvCount > 0` says part of the inventory is invisible to this credential — honestly incomplete, and it must keep blocking, by name.

**D-D — cleanup's `uncertain` state conflates post-dispatch doubt with pre-dispatch proof failure, and then refuses all reconciliation.** Live record (the stranded run's stored objects, read back 2026-10-28): both creation intents **cleaned** (AUD-K's reconciliation works live); the project object sits at `uncertain` — "Provider result uncertain; independent inspection required" — and every cleanup confirm short-circuits on that stored status without inspecting anything. The object reached `uncertain` because a pre-AUD-K inspect **threw** (the invented storage demand) and the apply loop's catch records every throw as `uncertain`. But an inspection throw proves nothing about any dispatch — in that object's history no delete ever dispatched — while the state's design purpose is the opposite case: a delete whose outcome is genuinely unknown must never be blindly retried. Two different situations, one terminal bucket, no exit.

**D-E — cleanup's deployment branch (the delete leg proper) demands the full shape and a preview target.** Found by the completed dossier audit, not by a probe: the branch required `row.projectId === project` (absent in two of three documented read-back shapes), a preview target via the matcher (the provider **promotes** a run's first deployment to production — D-B's live record — so a successful seed's deployment could never be deleted by its own cleanup), and it let a 404 on its first read throw into the `uncertain` bucket (the D-D poison, again). The alias demand in the same branch **is** contract-sound (every documented shape carries `alias`) and stays absolute. The alias-revocation branch's cross-check carried the same `projectId`/target demands against the aliased deployment and is corrected identically. Audited and left alone, with reasons recorded in the dossier: the env branch (the by-id env get carries every demanded field in all its branches), the bypass branch (its `productionDeployment*` checks name fields the documented project schema does not contain — vacuous, harmless, off this path), the sandbox branch (its session endpoint is outside the vendored snapshot — unmodeled, off this path), and `vercel_deploy_delete` (terminal-preview-only **by design**; its `prove()` gets the same when-carried `projectId` correction only if a future packet takes it up — it is not the lifecycle's delete leg and not this card's scope).

## Scope

**In:**
- **Verify read-backs (all three create tools):** `projectId` equality is required **when the read-back carries it** (absent in the in-progress and reduced shapes); the always-present anchors are the deployment id and the target match. The seed's verify additionally: `meta.rtc_run` is required when `meta` is carried, and a provider-**promoted** target (`production`) confirms alongside the preview matcher, since the provider promotes a first deployment and the run's own recorded objects + run meta carry the fixture's identity.
- **Env inventory (project-delete.js, the shared inspect):** a reply with `pagination` goes through `countComplete` as today; a reply with an `envs` array and an integer `hiddenProductionEnvCount` is complete **iff the count is 0** (the array is the whole visible inventory and nothing is hidden); a positive count throws the same incompleteness error, and the outcome text names the hidden count. Any other shape stays incomplete.
- **Cleanup uncertain-state reconciliation (dev-runs.js):**
  - *Pre-dispatch proof failures are `blocked`, never `uncertain`.* In `deleteExactObject`, the project branch's head read and both inspect calls, and both intent branches' reconciliation reads, convert failures into blocked outcome strings instead of throwing into the apply loop's catch. `uncertain` is reserved for doubt after a dispatch (the delete write itself, the post-delete read-back).
  - *`uncertain` project and intent objects reconcile by inspection.* The apply loop's stored-status short-circuit now applies only to other object types; `deleteExactObject` admits `uncertain` project/intent objects into the same inspection-first flow as `active`/`blocked`. This is structurally incapable of a blind retry: an intent never dispatches, and a project whose feared delete actually landed reads back **absent** (cleaned, no dispatch), while a present project is inspected and then deleted exactly once in the pass. Other types (deployment, env, bypass) keep the manual-readback rule untouched.
- **Cleanup deployment + alias branches (D-E):** identity is the deployment id plus the run's recorded provenance — `projectId` (or the reduced shape's `project.id`) and `meta.rtc_run` are required **when carried**; the target is not an identity proof inside the run's own scratch project (promotion, D-B); the alias demand stays absolute (carried by every documented shape); a 404 on the deployment branch's first read is an absence proof (cleaned), not an `uncertain` poison.
- **Tests:** seed verify against in-progress and reduced read-back shapes, against a promoted (production) read-back, and a wrong-project full-shape control that must still refuse; from-files and from-git verifies against an in-progress read-back; env inventory branch-2 (count 0 deletes cleanly through `vercel_project_delete`; count > 0 blocks with zero DELETEs); cleanup: a stranded-shape run (project pre-marked `uncertain`, intents cleaned) discharges end-to-end in one confirm; an uncertain **deployment** object still stops at manual readback; an inspect failure (env list rejects) lands the project at `blocked`, not `uncertain`; a successful-seed run whose deployment was **promoted** discharges fully (deployment deleted before its project, exactly two DELETEs); a deployment whose read-back is the in-progress shape discharges.

**Out (non-goals):** the AUD-L-era re-probe run's discharge — its deployment exists at the provider but was never recorded into its run (the pre-fix create threw first), so its intent reconciles to *blocked — never recorded* by design, its project is not empty, and no tool on the current surface deletes a READY promoted deployment outside cleanup's recorded-run flow (`vercel_deploy_delete` is terminal-preview-only by design). Its teardown is an owner dashboard action at closure time (the S7 fixture precedent); an intent *adoption* capability (recording a meta-proven run-owned deployment into its run so cleanup can take it) is a designed-but-unbuilt option, recorded here, not improvised. ## Review fixes (PR #255, 2026-10-28 — all three Codex findings accepted and fixed)

1. **Production-target acceptance is scratch-gated.** The D-E doctrine over-generalized: cleanup runs also record deployments in *existing user projects* (dev previews), where a preview later promoted to production must keep the refusal. The deployment branch (and the alias branch's production arm) now accept a non-preview target only when the deployment's project is **proven** to be the run's own seeded scratch project — projects_get read-back, id match, deterministic `rtc-<run>-` name. Everywhere else the preview refusal stands.
2. **Project absence is proven independently.** The project branch's inspect catch treated any 404 — including one from an inventory read inside the inspect — as project absence. Absence now requires an independent projects_get read-back 404; inventory failures land `blocked`.
3. **Nested project identity is checked, not skipped.** The create verifies and shapeResults (AUD-L/AUD-M when-carried rules) now resolve carried identity as `projectId ?? project.id` — a reduced-shape read-back naming a *different* project via `project.id` can no longer confirm.
