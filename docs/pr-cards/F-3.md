## Scope (catalog: "Routes, redirects and cache" — 8 tools)

Staging writes (`P`: `production()` false — nothing changes for visitors

## Build contract

- Fifteen operations: routes list/stage-add/stage-replace/stage-delete/
  route-update/versions-list/versions-update, redirects
  list/stage-replace/update/delete/restore-items/versions-list/
  versions-update, and the two edge-cache invalidate POSTs. The
  `dangerously-delete-*` operations are NEVER registered or called
  (design F5); a grep test asserts their absence from `src/`.
- Staging tools take a discriminated `action` per call (routes:
  add/update/remove/replace; redirects: replace/update/remove/
  restoreItems), preview the staged change in words with the reminder
  that visitors see no change until publish, re-check drift before
  dispatch (routes: the live version id + rule fingerprint; redirects:
  the live version alias + count), and journal an inverse (routes:
  discard the staged version the write created; redirects: the same;
  publish: restore the previously live version).
- The bulk-redirects PUT body carries `teamId` **in the body** beside
  `projectId` (contract requirement); the tool injects the selected
  account's team id — callers never supply it.
- Redirect remove/restore-items bodies carry `redirects` as an array of
  source **strings** (proven against the snapshot during the build —
  the PUT/PATCH item objects do not apply there).
- Build addendum (2026-10-30): the redirect item's `statusCode` is
  `oneOf [number, string]` and the repo validator compiles with
  `coerceTypes`, so a numeric statusCode matches both branches and can
  never validate (the string form passes). A narrow conditional
  exemption in `validateRequest` — the F-2 precedent — skips body
  validation for `bulk_redirects_stage`/`bulk_redirects_update` only
  when an item carries a numeric statusCode, keeping the caller's
  documented numeric form on the wire; all other bodies validate fully.
- Publish/restore read the versions list first and refuse unknown version
  ids and no-op targets (promoting the live version; discarding the live
  version). Verify is an independent versions read-back (`isLive`).
- Route/redirect inputs are bounded plain-JSON shapes validated in the
  tools (strings with caps, status codes 300–399, booleans); provider
  request validation also applies (no snapshot ambiguity is documented
  for these bodies — any that surfaces gets the F-2 treatment: prove it,
  exempt narrowly, record it here).
- Reads tolerate the documented empty-object response branch: it is
  reported as unverifiable (`routes: null`), never as an empty inventory.
- Cache invalidation takes exactly one of `tags` / `srcImages` and an
  optional `target`. No read-back exists for cache state, so verify
  reports `confirmed: null` with the dispatch receipt — never a claim.
- No inverse for cache invalidation (invalidation cannot be un-done; the
  content simply refetches).
